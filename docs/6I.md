# docker compose up --buildの流れI：ログと止め方（6I）

`docs/06.md`のI（98〜100）を詳しくしたもの。

コードブロックの1行目に、抜き出したファイルと行番号を書いている。

ライブラリのコードは`.venv/lib/python3.15/site-packages/`からの相対パスで書く。

コードやログは、iPhoneの縦画面で読めるよう、改行やインデントを変えたり、一部を省いたりしている。

出力は、2026-11-27に手元で実行して取ったもの（Docker 29.7.2、Compose v5.5.0）。ログの時刻はUTC（日本時間の9時間前）。

## 全体像

- ログ：コンテナのプロセスの出力が、どこを通って画面に出るか（1章）。
- 止める：Ctrl+Cで、Composeがweb → redisの順にコンテナを止め、gunicornとRedisがそれぞれの手順で終わる（2章）。
- 止めた後：コンテナ・ネットワーク・ボリュームのどれが残るか（3〜5章）。

`docker compose up --build`（`-d`なし）を動かしている端末でCtrl+Cを押したときの流れ（`compose`のプロセスにSIGINTを送って試した）：

```text

21:33:01.022 web   Handling signal: term
21:33:01.023 web   Worker exiting (pid: 8)
21:33:01.023 web   Worker exiting (pid: 9)
21:33:01.426 web   Shutting down: Master
21:33:01.468 webのコンテナが止まる
21:33:01.928 redis Received SIGTERM scheduling
                   shutdown...
21:33:02.027 redis User requested shutdown...
21:33:02.067 redis Redis is now ready to exit, bye
                   bye...
21:33:02.080 redisのコンテナが止まる
```

（コンテナが止まった時刻は`docker inspect`の`State.FinishedAt`、それ以外はログ。全体で約1.1秒）

## 1. ログの流れ

1. コンテナのPID 1の標準出力と標準エラーは、パイプになっている。標準入力は`/dev/null`。

```text
$ ls -l /proc/1/fd    （webの中）
0 -> /dev/null
1 -> pipe:[5486807]
2 -> pipe:[5486808]
...
```

2. パイプのもう一方の端は`containerd-shim`（`docs/6D.md`の35）で、そこからdockerdに送られる。\
   dockerdは、ログのドライバー`json-file`で、1行を1つのJSONにして`/var/lib/docker/containers/<コンテナID>/<コンテナID>-json.log`に書く（標準出力か標準エラーかと、受け取った時刻も一緒に書く）。
3. どちらに出るかは、プログラムによって違う。
   - gunicornのアクセスログ：標準出力（`--access-logfile -`）
   - gunicornのそのほかのログ（`Starting gunicorn`など）：標準エラー
   - Alembicのログ：標準エラー（`docs/6F.md`の28）
   - Redisのログと`Starting Redis Server`：標準出力
4. `-d`なしの`up`では、Composeが起動の前にコンテナの出力につなぎ（`docs/6D.md`の18）、`web-1    | `のようにサービスの名前を付けて表示する（名前の幅をそろえ、サービスごとに色を変える）。
5. `-d`を付けると、Composeは起動したところで終わる。ログはdockerdが書き続けているので、後から`docker compose logs`で見られる（`-f`で流し続け、`--timestamps`でdockerdが受け取った時刻を付ける）。

```text
web-1  | 2026-11-26T21:33:01.022809364Z
  [2026-11-26 21:33:01 +0000] [1] [INFO]
  Handling signal: term
```

（`--timestamps`を付けた例。先頭がdockerdの時刻、`[ ]`の中がgunicornの時刻）

6. Ctrl+Cを押した後は、Composeはコンテナのログを流さない。\
   上の全体像の`Handling signal: term`などは、端末には出ず、`docker compose logs`で見たもの。
7. ログのファイルは、コンテナを消す（`down`・`docker rm`）まで残る。\
   `json-file`にオプションを付けていないので、大きさに上限はない。長く動かすなら、`compose.yaml`の`logging:`で`max-size`などを付ける。

## 2. Ctrl+Cで止まるまで

8. Ctrl+Cは、端末で前面に動いているプロセス（Compose）にSIGINTを送る。\
   コンテナには端末（tty）も標準入力もつながっていないので、コンテナのプロセスにSIGINTが届くことはない。
9. Composeは、依存の逆順（web → redis）にコンテナを止める。redisは、webが止まり終わってから止める。

```text
 Compose Stopping Gracefully Stopping...
   press Ctrl+C again to force
 Container fl-demonstro-web-1 Stopping
 Container fl-demonstro-web-1 Stopped
 Container fl-demonstro-redis-1 Stopping
 Container fl-demonstro-redis-1 Stopped
```

10. 1つのコンテナを止める手順（`docker stop`と同じ）：
    - PID 1に`StopSignal`を送る。イメージにも`compose.yaml`にも書いていないので、SIGTERM（イベントでは`container kill`）。
    - `StopTimeout`の間、PID 1が終わるのを待つ。書いていないので10秒（`compose.yaml`の`stop_grace_period`で変えられる）。
    - 終わらなければSIGKILLで止める。
11. gunicornのログに`term`とあるのは、Ctrl+CのSIGINTではなく、Dockerが送ったSIGTERMを受けたから。
12. Composeは、2つとも止め終わると、終了ステータス130（128＋SIGINTの2）で終わる。

### gunicorn

```python
# gunicorn/arbiter.py:318-320
def handle_term(self):
    "SIGTERM handling"
    raise StopIteration
```

13. masterのハンドラーがSIGTERMをキューに入れ、メインのループが`Handling signal: term`を出して`handle_term()`を呼ぶ（`docs/6G.md`の6章）。\
    `StopIteration`を、`run()`が受けて`halt()`を呼ぶ。

```python
# gunicorn/arbiter.py:400-408
def halt(self, reason=None, exit_status=0):
    """ halt arbiter """
    # Stop control socket server first
    self._stop_control_server()

    self.stop()

    log_func = (self.log.info if exit_status == 0
                else self.log.error)
    log_func("Shutting down: %s", self.master_name)
```

```python
# gunicorn/arbiter.py:442-470
def stop(self, graceful=True):
    ...
    sock.close_sockets(self.LISTENERS, unlink)

    self.LISTENERS = []
    sig = signal.SIGTERM
    if not graceful:
        sig = signal.SIGQUIT
    limit = time.time() + self.cfg.graceful_timeout
    ...
    self.kill_workers(sig)
    ...
    while ((self.WORKERS or self.dirty_arbiter_pid)
           and time.time() < limit):
        ...
        self.reap_workers()
        self.reap_dirty_arbiter()
        time.sleep(0.1)

    self.kill_workers(signal.SIGKILL)
```

（docstringと、使っていない機能の部分は省略）

14. `halt()`は、まず管理用のソケット（`docs/6G.md`の4章）のスレッドを止める。
15. `stop()`は、masterが持っている待ち受けのソケットを閉じる。\
    ワーカーも同じソケットを持っていて、終わるときに閉じる。全員が閉じると、新しい接続は断られる。
16. ワーカーにSIGTERMを送り、全員が終わるか`--graceful-timeout`（30秒）が過ぎるまで、0.1秒ごとに回収する。\
    残ったワーカーには、最後にSIGKILLを送る。
17. ワーカーは、SIGTERMで`self.alive = False`にするだけ（`docs/6G.md`の26）。
    - リクエストを処理している最中なら、それを最後まで終えてから、ループを抜ける。
    - 待っている最中なら、シグナルで自分を起こすパイプに書き込まれ、`select()`から抜けて、すぐにループを抜ける。

    ループを抜けると`init_process()`から戻って`sys.exit(0)`し、`spawn_worker()`の`finally`で`Worker exiting (pid: 8)`を出す（`gunicorn/arbiter.py:753・769-770`）。
18. 今回は2つとも待っている最中だったので、SIGTERMの1ミリ秒後に終わった。\
    masterの`Shutting down: Master`は、その0.4秒後（管理用ソケットのスレッドの終了と、0.1秒ごとの回収のため）。
19. masterが`sys.exit(0)`で終わると、PID 1が終わるのでコンテナが止まる（終了ステータス0）。\
    ワーカーが持っていたRedisへの接続は、プロセスが終わるときにOSが閉じる。

### Redis

```text
1:signal-handler (1795728781) Received SIGTERM
  scheduling shutdown...
1:M 21:33:02.027 * User requested shutdown...
1:M 21:33:02.027 * Calling fsync() on the AOF file.
1:M 21:33:02.028 * Saving the final RDB snapshot
  before exiting.
1:M 21:33:02.029 * BGSAVE done, 1 keys saved,
  0 keys skipped, 235 bytes written.
1:M 21:33:02.046 * DB saved on disk
1:M 21:33:02.067 # Redis is now ready to exit, bye
  bye...
```

（日付を省き、長い行を折り返している）

20. Redisのシグナルのハンドラーは、「止める」という印を立てて、ログを1行出すだけ。\
    ハンドラーの中ではふつうのログの書式が使えないので、役割の欄が`signal-handler`、時刻がUNIX時間（秒）になっている。
21. 実際に止める処理は、1秒に10回動く定期処理（`serverCron`）が印を見て始める。今回は約0.1秒後。
22. 止める処理：
    - `Calling fsync() on the AOF file.`：AOFの書き込みを、ディスクに確定させる。
    - `Saving the final RDB snapshot before exiting.`：`save`が設定されている（`docs/6E.md`の38）ので、`dump.rdb`を書く。1つのキーは、`docs/6H.md`で作ったセッション。\
      次の起動では、`--appendonly yes`なのでAOFだけを読み、この`dump.rdb`は読まない。
    - `Redis is now ready to exit, bye bye...`：終了ステータス0で終わる。

### 10秒の上限

23. Dockerの待ち時間（10秒）は、gunicornの`--graceful-timeout`（30秒）より短い。\
    10秒以上かかるリクエストの途中で止めると、gunicornが待っている間にDockerがSIGKILLを送り、そのリクエストは途中で切れる。\
    合わせるなら、webに`stop_grace_period: 30s`を書くか、gunicornに`--graceful-timeout`で10秒より短い値を渡す。
24. もう一度Ctrl+Cを押すと、Composeは待たずにコンテナを強制的に止める（SIGKILL）。\
    gunicornもRedisも後始末をしないまま終わる。RedisのAOFは、書き込みのたびにファイルへ書いている（`docs/6E.md`の37）ので、マシンごと落ちない限りほとんど失わないが、`dump.rdb`は更新されない。
25. `entrypoint.sh`で`exec`を使わずにgunicornを起動していると、SIGTERMはPID 1のshに捨てられ、10秒待ってからSIGKILLになる（`docs/6F.md`の46）。\
    今回webが0.5秒ほどで止まったのは、gunicornがPID 1としてSIGTERMを受け取れているから。

## 3. 止めた後のコンテナ

26. 止めただけでは、コンテナは消えない。

```text
$ docker compose ps -a
fl-demonstro-redis-1  Exited (0) 7 seconds ago
fl-demonstro-web-1    Exited (0) 8 seconds ago
```

（名前と状態だけを表示した）

27. コンテナの書き込み可能なレイヤー（`/home/app/.gunicorn`など）・ログ・設定は残る。ネットワークとボリュームも残る。
28. もう一度`docker compose up`すると、同じコンテナを起動し直す（`Started`。作り直さない。`docs/6D.md`の4）。\
    IPアドレスは起動のたびに割り当て直されるので、前と同じとは限らない。
29. `docker compose stop`も、2章と同じ手順で止める（Composeのプロセスが端末に残っていないだけ）。

## 4. restart: unless-stoppedと止め方

30. `restart: unless-stopped`は、PID 1が自分で終わったとき（落ちた・`flask db upgrade`が失敗したなど）に、Dockerがコンテナを起動し直す（`docs/6F.md`の9〜11）。
31. `docker stop`・`docker compose stop`・Ctrl+Cで止めたコンテナは、「自分で止めた」と記録され、起動し直さない。\
    Dockerやパソコン（WSL）を起動し直しても、止めたままになる。
32. 自分で止めずに動いていたコンテナは、Dockerが起動し直したときに、もう一度起動される。\
    `restart: always`なら、自分で止めたコンテナも、Dockerの起動のときに起動される。
33. 今回のコンテナは、起動し直されていない（`docker inspect`の`RestartCount`は0）。

## 5. downとdown -v

```text
$ docker compose down
 Container fl-demonstro-web-1 Stopping
 Container fl-demonstro-web-1 Stopped
 Container fl-demonstro-web-1 Removing
 Container fl-demonstro-web-1 Removed
 Container fl-demonstro-redis-1 Stopping
 Container fl-demonstro-redis-1 Stopped
 Container fl-demonstro-redis-1 Removing
 Container fl-demonstro-redis-1 Removed
 Network fl-demonstro_default Removing
 Network fl-demonstro_default Removed
```

34. `down`は、2章と同じ手順で止めてからコンテナを消し、最後にネットワークを消す（今回は全体で1.7秒）。
35. 消えるもの：コンテナ（書き込み可能なレイヤーとログも）、ネットワーク。\
    残るもの：ボリューム、イメージ（`fl-demonstro-web`）、ビルドキャッシュ。

```text
$ docker volume ls
DRIVER    VOLUME NAME
local     fl-demonstro_db-data
local     fl-demonstro_redis-data
```

36. 次の`up`では、ネットワーク（`docs/6C.md`）とコンテナを作り直し、ボリュームはそのまま使う。\
    RedisはAOFから期限の切れていないキーを戻し（`docs/6E.md`の30）、`app.db`はheadなので、マイグレーションは何も流さない（`docs/6F.md`の37）。
37. `down -v`は、さらに`compose.yaml`のトップレベルの`volumes:`に書いたボリュームも消す（`external: true`のものは消さない）。

```text
 Volume fl-demonstro-docs_redis-data Removed
 Volume fl-demonstro-docs_db-data Removed
```

（別のプロジェクト名で試したときの出力の一部）

38. DB（ユーザー）とセッションが消えるので、次の`up`では、3つのマイグレーションがすべて流れ、RedisのAOFも新しく作られる（`docs/6E.md`の33・`docs/6F.md`の4章）。
39. `down --rmi local`を付けると、Composeがビルドしたイメージ（`image:`で名前を付けていないもの。`fl-demonstro-web`）も消す。
40. Composeのコマンドでは消えないもの：作り直したときに名前が外れた古いイメージ（`docs/6B.md`の54）と、ビルドキャッシュ。\
    それぞれ`docker image prune`・`docker builder prune`で消す。
