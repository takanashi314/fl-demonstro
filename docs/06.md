# docker compose up --buildの流れ（06）

`docker compose up --build`を実行してから、アプリが起動してリクエストを受け付けるまで（と止め方）の流れ。

コードやログの抜粋は、iPhoneの縦画面で読めるよう、改行やインデントを変えたり、一部を省いたりしている。

ログは、2026-11-22に手元でビルド済みのイメージを使って`docker compose up -d`を実行して取ったもの（Docker 29.7.2、Compose v5.5.0）。

ビルド（B）以外の流れは、`--build`を付けたときと同じ。

関係するファイルは`compose.yaml`・`Dockerfile`・`.dockerignore`・`docker/entrypoint.sh`。

## 全体像

`docker compose up --build`は、次の順に進む。

- A. Composeが設定を読む（1〜6）
- B. イメージを用意する（ビルド）（7〜31）
- C. ネットワークとボリュームを作る（32〜33）
- D. コンテナを作り、起動の順番を決める（34〜38）
- E. Redisが起動する（39〜54）
- F. webが起動し、マイグレーションを流す（55〜82）
- G. gunicornが起動する（83〜91）
- H. 最初のリクエスト（92〜97）
- I. ログと止め方（98〜100）

## A. Composeが設定を読む

（詳しくは`docs/6A.md`）

1. `docker compose up --build`により、Composeが、今いるフォルダの`compose.yaml`を読む。
2. 同じフォルダの`.env`を読み、`compose.yaml`の中の`${...}`を置き換える材料にする。\
   この`.env`は、コンテナに自動で渡されるわけではない。\
   コンテナに渡るのは、`environment:`に書いたものだけ。
3. `name: fl-demonstro`で、プロジェクト名が決まる。\
   ネットワーク・ボリューム・コンテナの名前の頭に付く。\
   書かないとフォルダ名が使われ、フォルダ名を変えるとボリュームの名前も変わってしまう。
4. `${SECRET_KEY:?...}`を置き換える。\
   `.env`に`SECRET_KEY`がないか空なら、メッセージを出してここで止まる（何も作られない）。
5. サービスは`web`と`redis`の2つ。\
   `web`に`depends_on: redis`があるので、redisを先に起動する順番になる。
6. 名前付きボリューム（`db-data`・`redis-data`）と、既定のネットワーク（`default`）を使うことが決まる。

## B. イメージを用意する（ビルド）

（詳しくは`docs/6B.md`）

7. `redis`は`image: redis:8-alpine`。\
   手元になければDocker Hubから取ってくる（pull）。\
   あれば、そのまま使う。
8. `web`は`build: .`。\
   `--build`を付けているので、毎回ビルドして`fl-demonstro-web`というイメージを作り直す（9〜31）。\
   中身が変わっていない段階はキャッシュが効くので、毎回すべてをやり直すわけではない（17）。\
   `--build`を付けないと、イメージが手元にあればそのまま使い、コードを変えても作り直さない。

9. プロジェクトのフォルダ（ビルドコンテキスト）をBuildKitに送る。\
   `.dockerignore`に書いたもの（`.env`・`.git`・`.venv`・`tests/`・`instance/`・`.docs/`など）は送らない。\
   `.env`の秘密の鍵は、イメージに入らない。
10. `Dockerfile`の1行目`# syntax=docker/dockerfile:1`に従い、Dockerfileを解釈するフロントエンドのイメージを取ってくる。
11. 1段目（`builder`）を`python:3.15-slim`から始める。
12. `COPY --from=ghcr.io/astral-sh/uv:0.13.5 /uv ...`で、uvの公式イメージからuvの実行ファイルだけをコピーする。
13. 環境変数を3つ設定する。
    - `UV_COMPILE_BYTECODE=1`：インストールのときに`.pyc`を作っておき、起動を速くする。
    - `UV_LINK_MODE=copy`：既定のclone（コピーオンライト）やハードリンクは同じファイルシステムの中でしかできず、キャッシュ（16）は別のファイルシステムなので、最初からコピーで入れる（切り替えの警告を出さない）。
    - `UV_PYTHON_DOWNLOADS=never`：イメージのPythonを使い、uvが別のPythonを取ってこないようにする。
14. `WORKDIR /app`。
15. `pyproject.toml`と`uv.lock`だけをコピーする。
16. `uv sync --locked --no-dev --no-install-project`で、依存パッケージだけを`/app/.venv`に入れる。
    - `--locked`：`uv.lock`が`pyproject.toml`と食い違っていたら失敗する。
    - `--no-dev`：devグループ（pytest・flask-debugtoolbarなど）は入れない。
    - `--mount=type=cache`：ダウンロードしたパッケージを、ビルドをまたいで使い回す。
17. 15〜16は`pyproject.toml`と`uv.lock`が変わらない限り、レイヤーのキャッシュが効く。\
    コードだけを変えたときは、ここを飛ばして速く終わる。
18. `README.md`と`src/`をコピーする。\
    `README.md`は、`pyproject.toml`の`readme`で指定しているので、パッケージを作るのに要る。
19. `uv sync --locked --no-dev --no-editable`で、アプリ自体を入れる。\
    ビルドバックエンド`uv_build`で`fl_demonstro`をパッケージ（wheel）にし、`.venv`のsite-packagesにインストールする。\
    `--no-editable`なので、コードはsite-packagesにコピーされ、`src/`がなくても動く。
20. 2段目を、もう一度`python:3.15-slim`から始める。\
    1段目の中身は捨てるので、uvやビルド用のファイルは最終的なイメージに入らない。
21. `groupadd`と`useradd --system --create-home app`で、専用のユーザー`app`を作る。\
    ホームディレクトリ`/home/app`も作られる（90で使われる）。
22. `WORKDIR /app`。
23. 1段目から`/app/.venv`だけをコピーする。\
    同じ`python:3.15-slim`なので、仮想環境の中の`python`が指す先（イメージのPython）がそのまま使える。
24. `migrations/`をコピーする。\
    site-packagesには入らないので、`flask db upgrade`（76）のために別に置く。
25. `docker/entrypoint.sh`を`/usr/local/bin/`にコピーする。
26. `/app/instance`を作り、所有者を`app`にする。\
    SQLiteのファイルを、`app`ユーザーが作れるようにするため。
27. 環境変数を設定する。
    - `PATH`：先頭に`/app/.venv/bin`を足し、`gunicorn`・`flask`をそのまま呼べるようにする。
    - `PYTHONDONTWRITEBYTECODE=1`：実行中に`.pyc`を書かない。
    - `PYTHONUNBUFFERED=1`：出力をためずにすぐ出す（ログがすぐ見える）。
    - `FLASK_APP=fl_demonstro`：`flask`コマンドが読み込むアプリ。
    - `APP_ENV=production`：本番用の設定を選ぶ。
    - `INSTANCE_PATH=/app/instance`：instanceフォルダの場所。
28. `USER app`：コンテナの中のプロセスを`app`ユーザーで動かす。
29. `EXPOSE 8000`：このポートを使うという宣言。\
    実際にパソコンから開けるようにするのは、`compose.yaml`の`ports`。
30. `ENTRYPOINT ["entrypoint.sh"]`と`CMD [...]`を設定する。\
    起動時には、`entrypoint.sh`にgunicornのコマンドが引数として渡される。
31. 出来上がったイメージに`fl-demonstro-web`という名前が付く。

## C. ネットワークとボリュームを作る

（詳しくは`docs/6C.md`）

32. ネットワーク`fl-demonstro_default`（bridge）を作る。\
    今回は172.18.0.0/16で、ゲートウェイは172.18.0.1だった。
33. ボリューム`fl-demonstro_db-data`と`fl-demonstro_redis-data`がなければ作る。\
    すでにあれば、前のデータごとそのまま使う。

```text
Network fl-demonstro_default Created
Container fl-demonstro-redis-1 Created
Container fl-demonstro-web-1 Created
Container fl-demonstro-redis-1 Started
Container fl-demonstro-web-1 Started
```

（`docker compose up -d`の出力を短くしたもの）

## D. コンテナを作り、起動の順番を決める

（詳しくは`docs/6D.md`）

34. コンテナ`fl-demonstro-redis-1`を作る。
35. コンテナ`fl-demonstro-web-1`を作る。
    - 環境変数：イメージの`ENV`（27）に、`compose.yaml`の`environment`（`SECRET_KEY`・`REDIS_URL`・`SESSION_COOKIE_SECURE`）が足される。
    - ボリューム`db-data`を`/app/instance`に付ける。
    - パソコンの`127.0.0.1:8000`を、コンテナの`8000`につなぐ。\
      `127.0.0.1`なので、同じネットワークのほかの機器からは開けない。
    - `restart: unless-stopped`：自分で止めない限り、終了したらDockerが起動し直す。
36. 2つのコンテナをネットワークにつなぎ、IPアドレスを割り当てる。\
    今回はredisが172.18.0.2、webが172.18.0.3。\
    サービス名（`redis`・`web`）が、そのままホスト名としてDockerのDNSに登録される。
37. `depends_on`の順に起動する。\
    redisを起動し、「起動した」状態になってからwebを起動する。
38. `depends_on`の短い書き方は、コンテナが起動したところまでしか待たない。\
    Redisが接続を受け付けられる状態（52）になったかは待たない。\
    それでも困らないのは、アプリがRedisにつなぐのが、実際に必要になったとき（96）だから。

## E. Redisが起動する

（詳しくは`docs/6E.md`）

39. ボリューム`redis-data`を`/data`に付ける（イメージの作業フォルダも`/data`）。
40. Dockerが、イメージの`docker-entrypoint.sh`をrootで実行する。\
    引数は`compose.yaml`の`command`。

```text
redis-server --appendonly yes --maxmemory 128mb
  --maxmemory-policy allkeys-lru
```

41. スクリプトは、最初の引数が`redis-server`なので、サーバーの起動だと判断する。
42. rootで動いているので、`/data`の中（`*.rdb`と`appendonlydir`）のうち、redisユーザーが読み書きできないものの所有者を直す。
43. `setpriv`でredisユーザーに切り替え、余分な権限（capabilities）を落として、スクリプト自身を実行し直す。
44. 2回目はrootではないので、権限の直しは飛ばす。\
    umaskを`0077`にする（作るファイルを本人しか読めないようにする）。
45. `Starting Redis Server`と出し、`/usr/local/lib/redis/modules/`にあるモジュールを`--loadmodule`で引数に足す。
46. `exec`で`redis-server`を実行する。\
    コンテナのPID 1が`redis-server`になる。
47. Redis 8.10.3が起動する。\
    カーネルの`vm.overcommit_memory`の警告が出る。\
    これはホスト（今回はWSL）の設定の話で、アプリの動きには関係しない。
48. 同時に開けるファイルの数の上限を、1024から10032に上げる（接続数の上限10000と予備32）。
49. 同梱のモジュール（RedisBloom・RediSearch・RedisTimeSeries・RedisJSON）を読み込む。\
    このアプリは使っていない。
50. `Server initialized`。
51. `--appendonly yes`なので、`/data/appendonlydir`のAOFからデータを読み込む。\
    manifestに従い、base（RDB形式）→ incr（追記分）の順に読む。\
    前回までのセッションや送信回数の記録が、ここで戻る。
52. `Ready to accept connections tcp`：6379番で接続を受け付け始める。
53. 「認証がなく、ネットワークの制限もない」という警告が出る。\
    公式イメージはprotected modeが切ってある（`CONFIG GET protected-mode`は`no`）。\
    `compose.yaml`で`ports`を書いていないので、届くのは同じネットワークのコンテナ（web）だけ。
54. `maxmemory`は128MB（134217728バイト）、`maxmemory-policy`は`allkeys-lru`。\
    いっぱいになると、しばらく使われていないキーから消す。

```text
Starting Redis Server
Redis version=8.10.3
Configuration loaded
Increased maximum number of open files to 10032
Module 'search' loaded
Server initialized
Reading RDB base file on AOF loading
DB loaded from append only file
Ready to accept connections tcp
```

（Redisのログを短くしたもの）

## F. webが起動し、マイグレーションを流す

（詳しくは`docs/6F.md`）

55. ボリューム`db-data`を`/app/instance`に付ける。\
    新しく作ったボリュームには、イメージの`/app/instance`の中身と所有者（26の`app:app`）がコピーされる。\
    そのため、`app`ユーザーが`app.db`を作れる。
56. Dockerが`app`ユーザー（uid 999）で`entrypoint.sh`を実行する。\
    引数はgunicornのコマンド（30）。\
    この時点のPID 1はシェル（`sh`）。
57. `set -e`：この後のコマンドが失敗したら、スクリプトをそこで止める（gunicornを起動しない）。
58. `flask db upgrade`を実行する。
59. `flask`コマンドは`.env`を探すが、イメージにはない（9）。\
    設定は、すべて環境変数から来る。
60. `FLASK_APP=fl_demonstro`なので、site-packagesの`fl_demonstro`をimportする。
61. `fl_demonstro/__init__.py`の先頭で`config.py`がimportされ、クラスの本体が実行される。\
    環境変数の値が、ここで属性に入る。
    - `SECRET_KEY`：composeから渡された値
    - `REDIS_URL`：`redis://redis:6379/0`。`RATELIMIT_STORAGE_URI`も、これに合わせてRedisになる。
    - `DATABASE_URL`：ないので`sqlite:///app.db`
    - `TRUSTED_PROXY_COUNT`：ないので0
    - `ProductionConfig.SESSION_COOKIE_SECURE`：`"false"`なので`False`（`REMEMBER_COOKIE_SECURE`も同じ）
62. `errors`・`extensions`・`security`もimportされ、拡張機能のオブジェクト（`db`・`limiter`など）が作られる。
63. `flask`コマンドが、パッケージの中から`create_app`という名前の関数を見つけ、引数なしで呼ぶ。
64. `_instance_path()`：`INSTANCE_PATH`があるので`/app/instance`。
65. `get_config()`：`APP_ENV=production`なので`ProductionConfig`。\
    `from_object()`で、大文字の属性が`app.config`にコピーされる。
66. `SECRET_KEY`があるので、先に進む。
67. `TRUSTED_PROXY_COUNT`が0なので、ProxyFixは付けない。
68. `db.init_app()`：相対パスの`app.db`を`/app/instance/app.db`にして、エンジンを作る。\
    まだ接続はしない。
69. `migrate.init_app()`：`flask db`コマンドが使えるようになる。
70. `csrf.init_app()`・`limiter.init_app()`。\
    回数の記録先としてRedisのクライアントを作り、Luaスクリプトも登録する。\
    ただし、Redisにはまだつながない。
71. `login_manager.init_app()`。
72. `_configure_session_storage()`：`SESSION_TYPE`がなく`REDIS_URL`があるので、セッションの保存先をRedisにする（`Redis.from_url()`。まだつながない）。
73. `server_session.init_app()`。
74. `_init_debug_toolbar()`：デバッグモードではないので、何もしない（ツールバーは本番のイメージに入ってもいない）。
75. `init_security()`・`init_error_handlers()`・ブループリントの登録で、`create_app()`が終わる。\
    （61〜75の`__init__.py`の動きは、`docs/6A.md`の7章で詳しく書いている）
76. `flask db upgrade`の本体として、`migrations/env.py`が実行される。\
    `alembic.ini`のログ設定も読まれる。
77. Flask-Migrateを通じてエンジンを取り出し、DBに接続する。\
    ここで初めて`/app/instance/app.db`を開く（なければ作る）。
78. Alembicがログを出す。

```text
INFO [alembic.runtime.migration] Context impl SQLiteImpl.
INFO [alembic.runtime.migration] Will assume
  non-transactional DDL.
```

79. `alembic_version`テーブルで今の版を確かめ、head（`85dd7755e1ac`）までの未適用のマイグレーションを順に流す。\
    新しいボリュームなら、`d96ac129be18` → `e7469dcb534f` → `85dd7755e1ac`の3つが流れ、`Running upgrade`のログが出る。\
    今回はもうheadだったので、何も流れなかった。
80. `flask`コマンドが終わり、そのプロセスは終了する。\
    ここまでで、Redisには一度もつないでいない。
81. マイグレーションが失敗すると、`set -e`（57）でスクリプトが止まり、コンテナが終了する。\
    `restart: unless-stopped`なので、Dockerがコンテナを起動し直す。
82. `exec "$@"`で、シェルがgunicornに置き換わる。\
    gunicornがPID 1になり、`docker compose stop`のSIGTERMを直接受け取れる。

## G. gunicornが起動する

（詳しくは`docs/6G.md`）

83. gunicornが引数を読む。
    - `--bind 0.0.0.0:8000`：コンテナのすべてのアドレスの8000番で待つ。
    - `--workers 2`：ワーカーを2つ使う。
    - `--access-logfile -`：アクセスログを標準出力に出す。
    - `fl_demonstro:create_app()`：アプリの読み込み方。
84. masterプロセス（PID 1）が`Starting gunicorn 27.0.1`と出す。
85. `--preload`を付けていないので、masterはアプリを読み込まない。
86. masterが0.0.0.0:8000のソケットを作り、`Listening at`と出す。
87. ワーカーの種類は`sync`（1つのワーカーが、一度に1つのリクエストを処理する）。
88. masterがワーカーを2つforkする（今回はPID 8と9）。
89. 各ワーカーがアプリを読み込む。
    - `fl_demonstro:create_app()`を、関数の呼び出しとして解釈する。
    - `fl_demonstro`をimportする。ワーカーごとに`config.py`も評価される（61と同じ）。
    - `create_app()`を呼ぶ（64〜75と同じ）。
    - ワーカーは別々のプロセスなので、アプリ・エンジン・Redisのクライアントはワーカーごとに別になる。\
      メモリの中のものは共有されないので、セッションと送信回数の記録をRedisに置いている。
    - `SECRET_KEY`は環境変数から来るので、2つのワーカーで同じ値になる。
90. masterが、管理用のソケット`/home/app/.gunicorn/gunicorn.ctl`を開く。\
    gunicorn 25.1から入った機能で、`gunicornc`コマンドでワーカーの状態を見たりできる。\
    `useradd --create-home`で作ったホームディレクトリ（21）がここで使われる。
91. 起動が終わる。\
    ワーカーはソケットでリクエストを待ち、masterはワーカーを見張る。\
    ワーカーが応答しなくなったら（既定で30秒）、作り直す。

```text
[1] Starting gunicorn 27.0.1
[1] Listening at: http://0.0.0.0:8000 (1)
[1] Using worker: sync
[8] Booting worker with pid: 8
[9] Booting worker with pid: 9
[1] Control socket listening at
    /home/app/.gunicorn/gunicorn.ctl
```

（gunicornのログを短くしたもの。`[ ]`の中はプロセスの番号）

## H. 最初のリクエスト

（詳しくは`docs/6H.md`）

92. ブラウザで`http://127.0.0.1:8000/`を開く。
93. パソコンの127.0.0.1:8000に来た通信を、Dockerがwebコンテナの8000番に転送する（35）。
94. アプリから見た接続元は、ネットワークのゲートウェイの172.18.0.1になる。
95. どちらかのワーカーがリクエストを受け取り、Flaskが処理する。\
    `before_request`（CSRF・回数制限）→ ビュー → テンプレート → `after_request`（セキュリティ用ヘッダーなど）の順。
96. セッションを読み書きするとき、または回数を数えるときに、初めてRedisにつなぐ。\
    `redis`という名前は、DockerのDNS（コンテナの中の127.0.0.11）が172.18.0.2に変換する。\
    トップページを開くだけでは、Redisを使わないこともある。\
    ログイン画面を開くとCSRFトークンがセッションに入るので、そこでRedisに書き込まれる。
97. アクセスログが1行出る。

```text
172.18.0.1 - - [22/Nov/2026:20:15:31 +0000]
  "GET / HTTP/1.1" 200 2790 "-" "curl/8.5.0"
```

（今回はcurlで確かめた）

## I. ログと止め方

（詳しくは`docs/6I.md`）

98. `-d`を付けずに実行した場合（`docker compose up --build`）は、Composeがコンテナの出力を、`redis-1 | ...`・`web-1 | ...`の形でまとめて流し続ける。
99. Ctrl+C（または`docker compose stop`）で止める。
    - 依存の逆順（web → redis）に止める。
    - Dockerは各コンテナのPID 1にSIGTERMを送る。
    - gunicornは、処理中のリクエストを終えてから止まろうとする。
    - Redisは、データをファイルに書き出してから終了する。
    - 10秒たっても止まらなければ、SIGKILLで強制的に止める。
100. `docker compose down`なら、コンテナとネットワークも消す。\
