# conftest.py のフィクスチャの関係（05）

コードの抜粋は、iPhone の縦画面で読めるよう、元のファイルから改行やインデントを変えている（中身は同じ）。

対象は `tests/conftest.py` の `MakeApp`・`make_app`・`app`。

## 全体像

混乱しやすいのは、`make_app` という名前が2つのものを指しているから。

- フィクスチャの関数そのもの（`@pytest.fixture` を付けた `make_app()`）
- テストが引数 `make_app` で受け取る値（中で作る `_make_app` という関数）

登場するものは4つ。

- **`MakeApp`**
  - 正体：型。実行時には何もしない。
  - 誰が呼ぶか：誰も呼ばない。型ヒント専用。
- **`make_app`（フィクスチャ）**
  - 正体：`@pytest.fixture` を付けた関数。
  - 誰が呼ぶか：pytest だけ。
  - 結果：`_make_app` という関数を yield する。
- **`_make_app`**
  - 正体：`make_app` の中で作る関数。型は `MakeApp`。
  - 誰が呼ぶか：テスト（引数名 `make_app` で受け取って呼ぶ）。
  - 結果：Flask アプリ。
- **`app`（フィクスチャ）**
  - 正体：`@pytest.fixture` を付けた関数。
  - 誰が呼ぶか：pytest だけ。
  - 結果：`TestingConfig` の Flask アプリ。

## 1. コード

### `tests/conftest.py`（抜粋）

```python
MakeApp = Callable[
    [type[Config]],
    Flask,
]


@pytest.fixture
def make_app() -> Iterator[MakeApp]:
    apps: list[Flask] = []

    def _make_app(
        config_class: type[Config],
    ) -> Flask:
        app = create_app(config_class)
        with app.app_context():
            db.create_all()
        apps.append(app)
        return app

    yield _make_app

    for app in apps:
        with app.app_context():
            db.session.remove()
            db.drop_all()
            db.engine.dispose()


@pytest.fixture
def app(make_app: MakeApp) -> Flask:
    return make_app(TestingConfig)
```

（コメントと docstring は省略）

- `MakeApp` は「設定クラスを1つ受け取り、Flask アプリを返す関数」の型。\
  `_make_app` がまさにこの型。
- `app` フィクスチャの引数 `make_app` も、受け取るのは `_make_app`。

## 2. テストが `make_app` を受け取るとき

```python
def test_x(
    make_app: MakeApp,
) -> None:
    app = make_app(
        CSRFEnabledConfig,
    )
```

1. pytest が引数名 `make_app` を見て、同じ名前のフィクスチャを探す。
2. pytest がフィクスチャ関数 `make_app()` を呼び、`yield _make_app` まで進める。
3. yield された `_make_app` が、テストの引数 `make_app` に入る。
4. テストの `make_app(CSRFEnabledConfig)` は、実際には `_make_app(CSRFEnabledConfig)` を呼んでいる。\
   アプリができ、`apps` に記録される。
5. テストが終わると、pytest がフィクスチャの続き（`yield` の後ろ）を実行し、`apps` のアプリを片付ける。

テストの中の `make_app` は、フィクスチャの関数ではなく `_make_app`。

`_make_app` は外側の `apps` を閉包として持っているので、テストが何回呼んでも、すべて `apps` に記録される。

## 3. テストが `app` を受け取るとき

```python
def test_y(app: Flask) -> None:
    ...
```

1. pytest が `app` フィクスチャを呼ぼうとする。\
   `app` の引数に `make_app` があるので、先に `make_app` フィクスチャを準備する（2章の 2〜3 と同じで、`_make_app` ができる）。
2. `app(make_app=_make_app)` が呼ばれ、中で `_make_app(TestingConfig)` を実行してアプリを返す。
3. そのアプリが、テストの引数 `app` に入る。
4. テストが終わると、`make_app` の後片付けがこのアプリも片付ける。\
   `app` 自身には後片付けがない（`yield` ではなく `return`）。

`--setup-show` を付けると、この順番が見える（`client` を使うテスト。出力は短くしている）。

```text
SETUP    F make_app
SETUP    F app
SETUP    F client
test_footer_is_shown
TEARDOWN F client
TEARDOWN F app
TEARDOWN F make_app
```

- テストが書いたのは `client` だけでも、`client` → `app` → `make_app` と依存をたどって準備される。
- 後片付けは準備の逆順。\
  接続を閉じる `make_app` の後片付けは最後なので、`app`・`client` を使い終わってから行われる。
- 1つのテストの中では、各フィクスチャは1回だけ作られる。\
  テストが `app` と `client` の両方を書いても、`client` が使うアプリとテストに渡されるアプリは同じもの。

## 4. pytest がしていることのイメージ

`app` を使うテスト（3章）の流れを、普通の Python で書くと次のようになる。

```python
# フィクスチャ関数を呼ぶ
# （yield があるので、
#   ジェネレーターができる）
gen = make_app()

# yield まで進めて、
# 出てきた関数を受け取る
_make_app = next(gen)

# app フィクスチャ：
# _make_app(TestingConfig) を返す
app_obj = app(_make_app)

# テストを実行する
test_y(app=app_obj)

# yield の後ろ（後片付け）を実行する
next(gen, None)
```

実際の pytest はもっと複雑だが、流れはこのとおり。

ただし、テストの中でフィクスチャ関数を直接呼ぶことはできない（5章）。

## 5. 型ヒントの付き方

- **フィクスチャ関数 `make_app`**：`-> Iterator[MakeApp]`\
  `yield` があるので、この関数はジェネレーター（値を1つずつ出すもの）になる。\
  出すのは `MakeApp` 型の関数1つなので、`Iterator[MakeApp]`。
- **テストの引数 `make_app`**：`MakeApp`\
  テストが受け取るのは yield された値（`_make_app`）なので、`Iterator` は付かない。
- **`app` フィクスチャ**：引数は `make_app: MakeApp`、戻り値は `-> Flask`。
- **テストの引数 `app`**：`Flask`

`MakeApp` に名前を付けているのは、4つのテストファイルが引数の型ヒントに使うから。\
毎回 `Callable[[type[Config]], Flask]` と書くと長く、型を変えるときに全部直す必要がある。

テスト側が import するのは型の `MakeApp` だけで、フィクスチャの `make_app` は import しない（引数名で pytest が渡す）。

## 6. なぜ2つのフィクスチャがあるのか

- **`app`**\
  ほとんどのテストは `TestingConfig` のアプリ1つで足りるので、すぐ使えるアプリを渡す。
- **`make_app`**\
  CSRF や回数制限を有効にした設定でアプリを作りたいテスト用。\
  設定を選べて、1つのテストで何個でも作れる。

`app` を `make_app` の上に作っているので、どちらのアプリも `make_app` の後片付け（`db.engine.dispose()`）1か所で片付く。

以前は `make_app` が普通の関数で、後片付けができず、接続が閉じられないまま残っていた（`docs/04.md`）。

## 7. よくある間違い

### フィクスチャを import して呼ぶ

```python
from tests.conftest import make_app


def test_x() -> None:
    make_app()
```

```text
Failed: Fixture "make_app" called
directly. Fixtures are not meant
to be called directly,
```

（出力は折り返している）

`@pytest.fixture` を付けた関数は、pytest だけが呼ぶもの。\
テストからは引数で受け取る。

### 引数に書かずに使う

```python
def test_x() -> None:
    make_app(TestingConfig)
```

```text
NameError: name 'make_app' is not
defined
```

フィクスチャは、テストの引数に名前を書いたときだけ渡される。

### `create_app()` を直接呼ぶ

DB に接続するアプリを `create_app()` で作ると、`make_app` の `apps` に記録されないので、テストの後で `dispose()` されない。

接続が閉じられないまま残り、`ResourceWarning` の原因になる（`docs/04.md`）。

DB に接続しないテスト（`test_config.py`）だけは、`create_app()` を直接呼んでいる。
