# 全体の構成（03）

コードの抜粋は、iPhoneの縦画面で読めるよう、元のファイルから改行やインデントを変えている（中身は同じ）。

## 全体像

Flaskのアカウント機能（サインアップ・ログイン・ログアウト）を持つWebアプリ。

アプリケーションファクトリ（`create_app()`）とブループリントで組み立てる。

データはSQLite、セッションはサーバー側（Redisまたはファイル）に保存する。

本番はDockerでgunicornとRedisを動かす。

プロジェクト直下の構成：

- `src/fl_demonstro/`：アプリ本体（Pythonパッケージ）
- `tests/`：自動テスト（pytest）
- `migrations/`：データベースの形の変更履歴（Alembic）
- `docs/`：解説（この文書など）
- `docker/entrypoint.sh`：コンテナ起動時の処理
- `Dockerfile`：本番用イメージの作り方
- `compose.yaml`：DockerでwebとRedisを動かす設定
- `.github/workflows/ci.yml`：CI（GitHub Actions）の設定
- `pyproject.toml`：依存パッケージとツール（ruff・mypy・pytest・djlint）の設定
- `uv.lock`：依存パッケージのバージョンの固定
- `.python-version`：Pythonのバージョン（3.15）
- `.pre-commit-config.yaml`：コミット・プッシュ前の自動チェック
- `.env.example`：環境変数のひな形（`.env`にコピーして使う）
- `instance/`：SQLiteとセッションのファイル（Gitの対象外）

## 1. アプリ本体（`src/fl_demonstro/`）

- `__init__.py`：アプリを組み立てる`create_app()`
- `config.py`：設定（開発用・本番用・テスト用）
- `extensions.py`：拡張機能のオブジェクト（db・csrf・limiterなど）
- `security.py`：セキュリティ用ヘッダー（CSPなど）
- `errors.py`：エラー画面（404など）
- `utils.py`：安全なリダイレクト先の判定
- `main/`：ブループリントmain（トップページ）
  - `__init__.py`
  - `views.py`
- `accounts/`：ブループリントaccounts（サインアップ・ログイン・ログアウト）
  - `__init__.py`
  - `views.py`：画面の処理
  - `forms.py`：入力フォーム
  - `models.py`：Userモデル
  - `passwords.py`：パスワードのハッシュ化とパスワードポリシー
  - `data/`：よく使われるパスワードの一覧（gzip）
- `templates/`：HTMLテンプレート（`docs/02.md`）

役割で分けると次のようになる。

- **組み立て**：`__init__.py`\
  設定を読み、拡張機能・フック・ブループリントをアプリに結び付ける。
- **設定**：`config.py`\
  環境ごとの設定クラス。\
  環境変数から値を読む。
- **拡張機能**：`extensions.py`\
  アプリに結び付ける前の拡張機能のオブジェクト。
- **全ページ共通の処理**：`security.py`・`errors.py`・`utils.py`\
  レスポンスヘッダー、エラー画面、リダイレクト先の判定。
- **機能**：`main/`・`accounts/`\
  URLごとのビュー、フォーム、モデル。
- **表示**：`templates/`\
  Jinjaテンプレート。

## 2. `create_app()`：アプリの組み立て

### `src/fl_demonstro/__init__.py:81-117`

```python
def create_app(
    config_class: type[Config]
    | None = None,
) -> Flask:
    """アプリケーションファクトリ：
    Flask アプリを作って返す。

    config_class を省略すると、
    環境変数 APP_ENV に合った
    設定を使う。
    """
    app = Flask(
        __name__,
        instance_path=_instance_path(),
    )
    app.config.from_object(
        config_class or get_config()
    )

    if not app.config.get("SECRET_KEY"):
        raise RuntimeError(
            "SECRET_KEY が"
            "設定されていません。"
            ".env に SECRET_KEY=... を"
            "書いてください。"
        )

    _trust_reverse_proxy(app)

    # 拡張機能をアプリと結びつける
    db.init_app(app)
    migrate.init_app(app, db)
    csrf.init_app(app)
    limiter.init_app(app)
    login_manager.init_app(app)
    _configure_session_storage(app)
    server_session.init_app(app)
    _init_debug_toolbar(app)

    init_security(app)
    init_error_handlers(app)

    # ブループリントの登録
    # （accounts を読み込むとモデルも
    # 読み込まれ、Flask-Migrate が
    # テーブルを見つけられる）
    from fl_demonstro.accounts import (
        bp as accounts_bp,
    )
    from fl_demonstro.main import (
        bp as main_bp,
    )

    app.register_blueprint(main_bp)
    app.register_blueprint(accounts_bp)

    return app
```

1. `instance_path`：SQLiteやセッションのファイルを置く場所。\
   環境変数`INSTANCE_PATH`（Dockerでは`/app/instance`）、なければプロジェクト直下の`instance/`。
2. 設定：引数で設定クラスを渡されなければ、`APP_ENV`から選ぶ（3章）。\
   `SECRET_KEY`がなければ起動を止める。
3. `_trust_reverse_proxy()`：`TRUSTED_PROXY_COUNT`が1以上なら`ProxyFix`を挟む。\
   `X-Forwarded-For`などから本当の接続元を読む。
4. 拡張機能の`init_app()`：`extensions.py`で作っておいたオブジェクトを、このアプリに結び付ける。\
   セッションの保存先は`server_session.init_app()`の前に決める（`docs/01.md`の2章）。
5. `init_security()`・`init_error_handlers()`：全レスポンスへのヘッダーと、エラー画面のハンドラを登録する。
6. ブループリントの登録：ブループリントは`create_app()`の中でimportし、アプリに登録する。\
   `accounts`を読み込むと`views.py`経由で`models.py`も読み込まれ、`User`モデルが`db`に登録される。\
   そのためFlask-Migrateがテーブルを見つけられる。

アプリケーションファクトリにしている理由：

- テストで、設定を変えたアプリを何個でも作れる（`create_app(TestingConfig)`）。
- 拡張機能をモジュールの変数として持つので、ビューやモデルから`from fl_demonstro.extensions import db`で使える。

アプリを起動する入口は2つある。

- **`flask`コマンド**（`flask run`・`flask db upgrade`）
  - 使う場面：開発、マイグレーション
  - `create_app()`の見つけ方：`FLASK_APP=fl_demonstro`から`create_app`を自動で探す
  - `.env`：python-dotenvが読み込む
- **gunicorn**
  - 使う場面：Docker（本番）
  - `create_app()`の見つけ方：`fl_demonstro:create_app()`を直接呼ぶ
  - `.env`：読まない（compose.yamlの`environment`で渡す）

## 3. 設定（`config.py`）

- **`Config`**（共通の親）\
  環境変数から`SECRET_KEY`・`DATABASE_URL`・`REDIS_URL`などを読む。\
  CookieはHTTPSのみ。
- **`DevelopmentConfig`**（`APP_ENV=development`）\
  Cookieをhttpでも送る。\
  デバッグツールバーでリダイレクトを止めない。
- **`ProductionConfig`**（`APP_ENV=production`、未設定のときも）\
  CookieはHTTPSのみ（`SESSION_COOKIE_SECURE=false`で緩められる）。
- **`TestingConfig`**（`APP_ENV`では選べない。テストが直接渡す）\
  CSRF・回数制限を切る。\
  DBとセッションはメモリ。\
  Argon2を最小の強さにする。

`APP_ENV`が未設定なら本番用になる。

設定し忘れたときに、安全側（CookieはHTTPSのみ、デバッグなし）に倒れる。

`TestingConfig`はCSRF対策を切っているので、`APP_ENV`で選べないようにして、本番で使われる道を塞いでいる。

### 環境変数

- `SECRET_KEY`：セッション・CSRFトークンの署名の鍵\
  未設定なら起動しない。
- `APP_ENV`：設定クラスの選択\
  未設定なら`production`。
- `FLASK_APP`・`FLASK_DEBUG`：`flask`コマンドの対象とデバッグモード
- `DATABASE_URL`：データベースの場所\
  未設定なら`sqlite:///app.db`（`instance/app.db`）。
- `REDIS_URL`：セッションと回数制限の保存先\
  未設定なら、セッションは`instance/sessions/`、回数制限はメモリ。
- `RATELIMIT_STORAGE_URI`：回数制限だけ別の保存先にする\
  未設定なら`REDIS_URL`。
- `INSTANCE_PATH`：instanceフォルダの場所\
  未設定ならプロジェクト直下の`instance/`。
- `SESSION_COOKIE_SECURE`：本番用でhttpのまま試すときに`false`\
  未設定なら`true`。
- `TRUSTED_PROXY_COUNT`：前に置いたリバースプロキシの数\
  未設定なら`0`（ヘッダーを信用しない）。

## 4. 拡張機能（`extensions.py`）

- `db`：Flask-SQLAlchemy\
  データベース（モデルの定義と操作）。\
  制約名の付け方（`NAMING_CONVENTION`）を決めて、マイグレーションを安定させる。
- `migrate`：Flask-Migrate\
  テーブルの形の変更（Alembic）を`flask db`コマンドで扱う。
- `csrf`：Flask-WTF\
  POSTなどにCSRFトークンがなければ400にする。
- `limiter`：Flask-Limiter\
  送信回数の制限（既定の識別子はIPアドレス）。
- `server_session`：Flask-Session\
  セッションの中身をサーバー側に置く（CookieにはセッションIDだけ）。
- `login_manager`：Flask-Login\
  ログイン状態の管理。\
  ログインが必要なページで`accounts.login`に飛ばす。

拡張機能ではないが、パスワードのハッシュ化にargon2-cffi、開発時のみFlask-DebugToolbarを使う。

## 5. URLの一覧

- `GET /`\
  `main.index`：トップページ
- `GET・POST /accounts/signup`\
  `accounts.signup`：サインアップ\
  POSTは1分5回・1時間20回まで。
- `GET /accounts/signup/done`\
  `accounts.signup_done`：登録完了
- `GET・POST /accounts/login`\
  `accounts.login`：ログイン\
  失敗はIPごとに1分5回・1時間20回、ユーザー名ごとに1時間10回まで。
- `POST /accounts/logout`\
  `accounts.logout`：ログアウト\
  `@login_required`。
- `GET /static/<path>`\
  `static`：静的ファイル\
  Flaskが自動で作る（今はファイルなし）。

`accounts`は`url_prefix="/accounts"`なので、ビューに書いた`/login`が`/accounts/login`になる。

エンドポイント名は`ブループリント名.関数名`。

`url_for('accounts.login')`やテンプレートの`request.endpoint`で使う。

## 6. `accounts/`の中身

- **`models.py`**：`User`・`load_user()`
  - `users`テーブル（`id`・`username`・`password_hash`・`created_at`）。
  - ユーザー名は小文字だけで保存する（`@validates`で確認）。
  - `authenticate()`はユーザーがいないときもダミーの照合をして、応答時間からユーザー名の有無を推測させない。
  - 正しいパスワードで古い方式のハッシュなら保存し直す。
- **`forms.py`**：`SignupForm`・`LoginForm`
  - 入力チェック。
  - ユーザー名は`^[a-z0-9]{3,32}$`、重複は`validate_username()`で確認する。
  - パスワードは`validate_password()`でポリシーを確認する。
- **`passwords.py`**：`hash_password()`・`verify_password()`・`password_policy_error()`など
  - Argon2idでハッシュ化する。
  - 以前のscryptのハッシュも照合できる。
  - ポリシーは8〜128文字。\
    よく使われるパスワード・ユーザー名を含むもの・同じ文字の繰り返し・連続した文字を弾く。
- **`views.py`**：`signup`・`signup_done`・`login`・`logout`
  - 画面の処理。
  - ログイン状態が変わるときにセッションIDを作り直す（`docs/01.md`の4章）。
  - 回数制限のデコレータを付けている。
- **`data/common_passwords.txt.gz`**
  - よく使われるパスワード46,483件（SecListsのNCSC上位10万件を加工）。

## 7. 1リクエストの流れ

本番（Docker）で`POST /accounts/login`が来た場合。

1. gunicornのワーカーがリクエストを受け、WSGIでFlaskに渡す。\
   `TRUSTED_PROXY_COUNT`が1以上なら、先に`ProxyFix`が接続元を書き換える。
2. リクエストコンテキストの開始：URLを照合してエンドポイントを決める。\
   Flask-SessionがCookieのセッションIDでRedisからセッションを読む。
3. `before_request`（登録順）：
   1. Flask-WTF：CSRFトークンを確認する。\
      なければ400（`errors/error.html`）。
   2. Flask-Limiter：回数制限を確認する。\
      超えていれば429。
4. ビュー`login()`：`LoginForm`で入力を確認し、`User.authenticate()`で照合する。\
   成功ならセッションを作り直してリダイレクト、失敗ならフォームを400で再表示する（`render_template()`は`docs/02.md`）。\
   `current_user`は最初に使われたとき、`load_user()`でデータベースから読み込まれる。
5. 例外が起きたら：`errors.py`のハンドラが`errors/error.html`を描画する。\
   500のときはデータベースの操作を取り消してから出す。
6. `after_request`（登録と逆の順）：
   1. `security.py`：CSPなどのセキュリティ用ヘッダーを付ける。\
      ログイン中は`Cache-Control: no-store`。
   2. Flask-Login：「ログインしたままにする」のCookieを付ける・消す。
   3. Flask-Limiter：ログインに失敗していれば（302以外）回数を数える。
7. Flask-SessionがセッションをRedisに保存し、Cookieを付けてレスポンスを返す（`docs/01.md`の3章）。

## 8. データベースとマイグレーション

データベースはSQLite。

`sqlite:///app.db`のような相対パスは、Flask-SQLAlchemyがinstanceフォルダからのパスとして扱うので、`instance/app.db`になる。

テーブルの形の変更はFlask-Migrate（Alembic）で管理し、`migrations/versions/`に履歴が並ぶ。

1. `d96ac129be18`：`users`テーブルを作る
2. `e7469dcb534f`：ユーザー名を大文字・小文字を区別せずに一意にする
3. `85dd7755e1ac`：ユーザー名を小文字だけで保存する

上から順に積み重なっていて、最新（head）は`85dd7755e1ac`。

Dockerでは、コンテナを起動するたびに`docker/entrypoint.sh`が`flask db upgrade`を実行してからgunicornを起動する。

テストの多くは`db.create_all()`でモデルから直接テーブルを作る。

マイグレーションそのものは`tests/test_migrations.py`が実際に流して確かめる。

## 9. 実行環境

開発（ローカル）とDocker（本番相当）の違い：

- **起動**
  - 開発：`flask run`（ポート5000）
  - Docker：gunicorn・ワーカー2つ（`127.0.0.1:8000`）
- **設定**
  - 開発：`.env`の`APP_ENV=development`・`FLASK_DEBUG=1`
  - Docker：`APP_ENV=production`（Dockerfile）、値はcompose.yamlから
- **データベース**
  - 開発：`instance/app.db`
  - Docker：ボリューム`db-data`の`/app/instance/app.db`
- **セッション**
  - 開発：`instance/sessions/`（`REDIS_URL`未設定時）
  - Docker：Redis（ボリューム`redis-data`）
- **回数制限の記録**
  - 開発：メモリ（`REDIS_URL`未設定時）
  - Docker：Redis
- **デバッグツールバー**
  - 開発：表示（`FLASK_DEBUG=1`）
  - Docker：なし（開発用の依存はイメージに入れない）

### Dockerfile

- 2段階のビルド。\
  1段目でuvを使い、`uv.lock`どおりに依存パッケージとアプリを`.venv`に入れる（開発用の依存は入れない）。\
  2段目は`.venv`・`migrations/`・`entrypoint.sh`だけをコピーした小さなイメージ。
- 依存パッケージを先に入れるので、コードだけを変えたときは依存のインストールにキャッシュが効く。
- rootではない専用ユーザー`app`で動かす。

### compose.yaml

- `web`：Dockerfileからビルドしたアプリ。\
  `127.0.0.1:8000`で自分のパソコンからだけ開ける。\
  `SECRET_KEY`は`.env`から渡し、なければ起動しない。
- `redis`：セッションと回数制限の保存先。\
  AOFでディスクにも書き、メモリの上限は128MB（`docs/01.md`の7章）。

## 10. 開発ツールと品質チェック

- **uv**：依存パッケージとPythonの管理
  - 設定：`pyproject.toml`・`uv.lock`・`.python-version`
- **ruff**：lintと整形
  - 設定：`pyproject.toml`の`[tool.ruff]`
  - 動くタイミング：pre-commit・CI
- **mypy**：型チェック（`src/`・`tests/`、型注釈を必須にする厳しめの設定）
  - 設定：`[tool.mypy]`
  - 動くタイミング：pre-commit・CI
- **djlint**：テンプレートの整形とlint
  - 設定：`[tool.djlint]`
  - 動くタイミング：pre-commit・CI
- **pytest**：自動テスト（CIではカバレッジも測る）
  - 設定：`[tool.pytest.ini_options]`
  - 動くタイミング：pre-push・CI

pre-commitは、コミットの前にruff（修正→整形→確認）・djlint（整形→lint）・mypy、プッシュの前にpytestを動かす。

CI（`.github/workflows/ci.yml`）は、pushとPull Requestでruff・mypy・djlint・pytestを実行し、テスト結果の集計をGitHubの画面に出す。

Pythonのバージョンは`.python-version`から読むので、プロジェクトとCIで揃う。

## 11. テスト（`tests/`）

- `conftest.py`：共通の準備\
  フィクスチャ`make_app`（テスト用のアプリと空のDBを作り、テストの後で片付ける）・`app`・`client`、ユーザー作成・ログインの補助関数。
- `test_accounts.py`：サインアップ
- `test_auth.py`：ログイン・ログアウト、「ログインしたままにする」、`?next=`の安全確認
- `test_models.py`：`User`モデル（小文字での保存、一意制約、`authenticate()`・`load_user()`など）
- `test_passwords.py`：ハッシュ化・再ハッシュ・パスワードポリシー
- `test_session.py`：サーバー側セッション、セッションIDの作り直し、保存先の選択
- `test_security.py`：セキュリティ用ヘッダー・CSP・CSRF・回数制限・プロキシの扱い
- `test_config.py`：設定の選び方、`SECRET_KEY`の確認、instanceフォルダの場所、環境変数の読み方
- `test_errors.py`：エラー画面
- `test_main.py`：トップページ・ナビゲーションバー・フッター
- `test_debug_toolbar.py`：デバッグツールバーの表示条件
- `test_migrations.py`：マイグレーションを実際に流す
- `test_utils.py`：`is_safe_redirect_url()`

テストは`make_app`フィクスチャでアプリを作る（`app`フィクスチャは`make_app(TestingConfig)`）。

DBはメモリ上のSQLite、セッションはメモリで、Redisには一切つながらない。

CSRFや回数制限のテストは、`TestingConfig`を継承して該当の設定だけ有効にしたクラスを使う。
