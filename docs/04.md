# テストの SQLite 接続と ResourceWarning（04）

コードの抜粋は、iPhone の縦画面で読めるよう、元のファイルから改行やインデントを変えている（中身は同じ）。

ライブラリのコードは `.venv/lib/python3.15/site-packages/` からの相対パスで書く。

調べたときのバージョンは、Python 3.15.0（CI は 3.15.2）、Flask-SQLAlchemy 3.1.1、SQLAlchemy 2.1.9、pytest 9.2.0、pytest-cov 7.1.0。

## 全体像

CI の pytest で、`ResourceWarning: unclosed database in <sqlite3.Connection object at 0x...>` が出る（#5）。

テストは成功していて、手元の `uv run pytest` では出ない。

原因は次の3つが重なったこと。

- **接続を閉じていない**\
  テストごとにアプリを作り、アプリごとにエンジンができる。\
  エンジンは in-memory SQLite の接続を1本持ち続けるが、テストの後片付けで `dispose()` していない。
- **GC で捨てられると警告が出る**\
  接続は、エンジンが GC で回収されるときに捨てられる。\
  Python 3.13 から、`close()` されずに回収された `sqlite3.Connection` は `ResourceWarning` を出す。
- **`--cov` のときだけ表示される**\
  `ResourceWarning` は普段 ignore される。\
  pytest-cov が `--cov` のときにこのメッセージの警告を表示する設定を足し、CI は `--cov` 付きで pytest を実行する。

## 1. 現象

CI（`.github/workflows/ci.yml` の Run tests）の warnings summary には、次のような警告が並ぶ。

```text
tests/test_accounts.py::
  test_signup_validation[...]
  .../jinja2/nodes.py:140:
  ResourceWarning: unclosed
  database in <sqlite3.Connection
  object at 0x779d78e89b60>
    for name, arg in zip(
        self.fields,
        fields,

```

- `jinja2/nodes.py:140` と最後の `for` は「警告が出たときに動いていたコード」で、SQLite とは関係がない（5章）。
- summary の件数は53件。\
  ほかに、summary の後で標準エラーに59件、インタプリタの終了時に1件出ている。
- 手元で `uv run pytest --cov=src` を実行すると同じ警告が出る。\
  件数は実行ごとに変わる（49件・37件など）。

## 2. テストの DB とエンジン

### `src/fl_demonstro/config.py:117`

```python

    "sqlite:///:memory:"

```

- `TestingConfig` の DB は in-memory の SQLite。\
  ファイルを作らず、接続（`sqlite3.Connection`）の中にだけ DB がある。\
  接続を閉じると DB も消える。

### `flask_sqlalchemy/extension.py:610-616`

```python
if (
    url.database is None
    or url.database in {"", ":memory:"}
):
    options["poolclass"] = (
        sa.pool.StaticPool
    )

    if "connect_args" not in options:
        options["connect_args"] = {}

    options["connect_args"][
        "check_same_thread"
    ] = False
```

- Flask-SQLAlchemy は、in-memory の SQLite には `StaticPool` を使う。
- エンジン・プール・接続の関係は次のとおり。
  - エンジン（`Engine`）：DB への入口。プールを1つ持つ。
  - プール（`Pool`）：接続を作り、使い回す。
  - 接続：DBAPI の接続。SQLite なら `sqlite3.Connection`。
- `StaticPool` は接続を1本だけ作り、すべてのリクエストで同じ接続を使う。\
  in-memory の DB は接続を閉じると消えるので、プールが接続を持ち続ける必要がある。
- `check_same_thread=False` は、別のスレッドからも同じ接続を使えるようにする設定。

### `flask_sqlalchemy/extension.py:273-274`・`359`

```python
self._app_engines = (
    WeakKeyDictionary()
)
```

```python
engines = self._app_engines.setdefault(
    app,
    {},
)
```

- エンジンはアプリごとに作られ、`db._app_engines` に入る。
- `WeakKeyDictionary` はキー（アプリ）を弱参照で持つ。\
  アプリが回収されると、そのエントリは自動で消える。
- 値（エンジンの dict）は普通の参照で持つ。\
  アプリが生きている間は、エンジンもこのエントリから参照され続ける。

## 4. 接続が捨てられるまで

### 参照カウントと GC

CPython はオブジェクトを2つの仕組みで回収する。

- **参照カウント**\
  オブジェクトを指す参照が0になった時点で、すぐに回収する。
- **循環参照の GC**\
  A → B → A のように互いを指すオブジェクトは、外から指されなくても参照が0にならない。\
  これを見つけて回収するのが GC（`gc` モジュール）。\
  オブジェクトを作った数が閾値を超えると自動で走る。`gc.collect()` で明示的に走らせることもできる。

### アプリとエンジンは循環参照を含む

アプリは循環参照を含むので、テストが終わって参照がなくなっても、GC が走るまで残る。

エンジンも循環参照を含む。

`gc.get_referrers()` で調べると、次の2つが見つかった。

#### `sqlalchemy/engine/base.py:2967-2970`

```python
if query_cache_size != 0:
    self._compiled_cache = (
        util.LRUCache(
            query_cache_size,
            size_alert=(
                self._lru_size_alert
            ),
        )
    )
```

- エンジン → `_compiled_cache`（`LRUCache`）→ `_lru_size_alert`（エンジンのバウンドメソッド）→ エンジン、と一周する。

#### `sqlalchemy/engine/create.py:731-736`・`776-778`

```python
def first_connect(
    dbapi_connection,
    connection_record,
) -> None:
    c = base.Connection(
        engine,
        ...
    )
```

```python
event.listen(
    pool,
    "connect",
    first_connect,
    _once_unless_exception=True,
)
```

（型ヒントと引数の一部は省略）

- `first_connect` は `create_engine()` の中のクロージャで、外側の `engine` を参照している。
- エンジン → プール → イベントのリスナー（`first_connect`）→ エンジン、と一周する。

### GC が2回必要になる

アプリへの参照がなくなってから接続が捨てられるまでに、GC が2回走る必要がある。

1. **1回目の GC でアプリが回収される**\
   アプリが消えるので、`db._app_engines` のエントリも消える。\
   エンジンを指していたのはこのエントリなので、ここでエンジンが不要になる。\
   ただし、エントリが消えるのは今回の GC で回収するものが決まった後なので、エンジンは今回の対象に入らない。
2. **2回目の GC でエンジンが回収される**\
   エンジン・プール・接続がまとめて回収される。\
   このとき `sqlite3.Connection` が `close()` されないまま回収され、`ResourceWarning` が出る。

### 実験

```python
import gc
import warnings
import weakref

from fl_demonstro.extensions import db
from tests.conftest import make_app

warnings.simplefilter(
    "default",
    ResourceWarning,
)

app = make_app()
with app.app_context():
    engine = weakref.ref(db.engine)
app = weakref.ref(app)

print("1回目")
gc.collect()
print(app(), engine())

print("2回目")
gc.collect()
print(app(), engine())
```

- `weakref.ref()` は弱参照で、回収を妨げずに「まだ生きているか」を確かめられる（回収済みなら `None` を返す）。
- `app = weakref.ref(app)` で、アプリへの普通の参照をなくしている。

実行結果は次のとおり。

```text
1回目
None Engine(sqlite:///%3Amemory%3A)
2回目
.../doc_exp.py:23: ResourceWarning:
  unclosed database in
  <sqlite3.Connection object at
  0x763621b85620>
None None
```

（警告は標準エラーに出るので、実際の表示順は前後する）

- 1回目の `gc.collect()` の後は、アプリだけが消え、エンジンは残っている。
- 2回目の `gc.collect()`（23行目）でエンジンが消え、警告が出る。

### Python 3.13 からの警告

Python 3.13 から、`sqlite3.Connection` は `close()` されないまま回収されると `ResourceWarning` を出すようになった。

ファイルやソケットが閉じられずに回収されたときと同じ扱いで、リソースの閉じ忘れを知らせるための警告。

## 5. 警告が出る場所と件数

### 関係のないテストの場所として出る

警告は、GC が走ったときに動いていたコードの場所として出る。

GC はオブジェクトを作った数で自動的に走るので、どこで走るかは決まっていない。

CI では、次のような場所として出ていた。

- `jinja2/nodes.py`・`jinja2/visitor.py`（テンプレートのコンパイル）
- `sqlalchemy/engine/result.py`・`sqlalchemy/sql/type_api.py`（クエリの結果の処理）
- `configparser.py`（`test_migrations.py` が Alembic の設定を読むところ）

テストの名前も、`test_passwords.py`・`test_auth.py`・`test_session.py` など、警告の原因と関係のないものになる。

### summary に入らない警告

#### `_pytest/unraisableexception.py:27-29`

```python
def gc_collect_harder(
    iterations: int,
) -> None:
    for _ in range(iterations):
        gc.collect()
```

- pytest は終了処理（`pytest_unconfigure`）で、この関数を通して `gc.collect()` を1回呼ぶ（CPython の場合）。
- このとき回収されたエンジンの警告は、summary を出した後なので、件数に入らず標準エラーに出る（CI の59件）。
- この GC で回収された最後のアプリのエンジンは、もう1回の GC を待つ。\
  インタプリタの終了時に回収され、`<sys>:0: ResourceWarning` と出る（CI の1件）。

### 件数が変わる理由

GC が走るタイミングは、作ったオブジェクトの数で決まる。

coverage の有無や Python のパッチバージョンなどで数が変わると、テストの実行中に回収される分（summary の件数）と、終了処理で回収される分の割合も変わる。

## 6. 手元で見えない理由

### Python のデフォルトの警告フィルタ

`warnings.filters` の初期値は次の5つ。

- `default::DeprecationWarning:__main__`
- `ignore::DeprecationWarning`
- `ignore::PendingDeprecationWarning`
- `ignore::ImportWarning`
- `ignore::ResourceWarning`

`ResourceWarning` は ignore されるので、何も設定しなければ表示されない。

### `_pytest/config/__init__.py:1328-1332`

```python
with warnings.catch_warnings(
    record=record,
) as log:
    if not sys.warnoptions:
        warnings.filterwarnings(
            "always",
            category=DeprecationWarning,
        )
        warnings.filterwarnings(
            "always",
            category=(
              PendingDeprecationWarning
            ),
        )
```

- pytest はテストごとにこのフィルタで警告を記録し、warnings summary に出す。
- pytest が表示に切り替えるのは `DeprecationWarning` と `PendingDeprecationWarning` だけで、`ResourceWarning` は ignore のまま。

### `pytest_cov/plugin.py:330-334`

```python
for _, message, category, _, _ in (
    warnings.filters
):
    if (
        category is ResourceWarning
        and message in (
            COVERAGE_SQLITE_WARNING_RE,
            COVERAGE_SQLITE_WARNING_RE2,
        )
    ):
        break
else:
    warnings.filterwarnings(
        "default",
        "unclosed database in"
        " <sqlite3.Connection"
        " object at",
        ResourceWarning,
    )
```

- pytest-cov は `--cov` のとき、`pytest_runtestloop` でこのフィルタを足す。
- 目的は、coverage 自身の警告を扱うこと。\
  coverage は計測データを SQLite のファイル（`.coverage`）に保存するので、同じ警告を出すことがある。\
  `filterwarnings = ["error"]` のような厳しい設定でも、それがエラーにならないように `default` にしている。
- `filterwarnings()` の第2引数は、警告メッセージの先頭にマッチする正規表現。\
  アプリの接続の警告も同じメッセージで始まるので、このフィルタに当たって表示される。
- `default` は「同じ場所・同じメッセージの警告は1回だけ表示する」。\
  メッセージにはアドレス（`0x...`）が入って毎回違うので、実際にはすべて表示される。

### `.github/workflows/ci.yml:63-67`

```yaml
uv run --no-sync pytest \
  --junitxml=... \
  --cov=src \
  --cov-report=term-missing \
  --cov-report=...
```

（レポートの出力先は省略）

- CI は `--cov=src` 付きで pytest を実行する。手元の `uv run pytest` は `--cov` を付けない。
- つまり接続の閉じ忘れは手元でも毎回起きていて、警告が表示されるかどうかだけが違う。\
  手元でも `uv run pytest -W default::ResourceWarning` で見える。

## 7. 影響

- テストだけの問題。\
  本番は `create_app()` を1回だけ呼び、エンジンはプロセスが終わるまで使い続けるので関係しない。
- テスト中は、回収されるまで前のテストの in-memory DB がメモリに残る。

## 8. 直し方（#5 で対応する）

テストで作ったアプリのエンジンを、テストの終わりに `dispose()` する。

### `app` フィクスチャ

後片付けに `db.engine.dispose()` を足す。

```python
@pytest.fixture
def app() -> Iterator[Flask]:
    app = make_app()
    yield app
    with app.app_context():
        db.session.remove()
        db.drop_all()
        db.engine.dispose()
```

`-W default::ResourceWarning` を付けた実行で summary に出た57件のうち、55件はこのフィクスチャで作った接続だった（`PYTHONTRACEMALLOC` で作成元を確かめた）。

### テストの中で直接作るアプリ

3章の5つのファイルは、別に対応する必要がある。

例えば `make_app` を、作ったアプリをテストの後でまとめて片付けるフィクスチャ（factory）にする。

### 実験：すべてのエンジンを dispose する

作られたエンジンを記録し、各テストの後で `dispose()` する pytest プラグインを一時的に読み込んだ（リポジトリには入れていない）。

```python
import pytest
from flask_sqlalchemy import SQLAlchemy

engines = []
make_engine = SQLAlchemy._make_engine


def record(self, *args):
    engine = make_engine(self, *args)
    engines.append(engine)
    return engine


SQLAlchemy._make_engine = record


@pytest.hookimpl(wrapper=True)
def pytest_runtest_teardown(item):
    result = yield
    while engines:
        engines.pop().dispose()
    return result
```

- `-W default::ResourceWarning` でも `--cov=src` でも、SQLite の警告は summary・標準エラーとも0件になった。
- `dispose()` すれば警告が消えることの確認で、修正の方法はこのプラグインとは別に考える（`_make_engine` は Flask-SQLAlchemy の内部のメソッド）。
