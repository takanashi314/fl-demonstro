# テストのSQLite接続とResourceWarning（04）

コードの抜粋は、iPhoneの縦画面で読めるよう、元のファイルから改行やインデントを変えている（中身は同じ）。

ライブラリのコードは`.venv/lib/python3.15/site-packages/`からの相対パスで書く。

調べたときのバージョンは、Python 3.15.0（CIは3.15.2）、Flask-SQLAlchemy 3.1.1、SQLAlchemy 2.1.9、pytest 9.2.0、pytest-cov 7.1.0。

## 全体像

CIのpytestで、`ResourceWarning: unclosed database in <sqlite3.Connection object at 0x...>`が出る（#5）。

テストは成功していて、手元の`uv run pytest`では出ない。

原因は次の3つが重なったこと。

- **接続を閉じていない**：テストごとにアプリを作り、アプリごとにエンジンができる。\
  エンジンはin-memory SQLiteの接続を1本持ち続けるが、テストの後片付けで`dispose()`していない。
- **GCで捨てられると警告が出る**：接続は、エンジンがGCで回収されるときに捨てられる。\
  Python 3.13から、`close()`されずに回収された`sqlite3.Connection`は`ResourceWarning`を出す。
- **`--cov`のときだけ表示される**：`ResourceWarning`は普段ignoreされる。\
  pytest-covが`--cov`のときにこのメッセージの警告を表示する設定を足し、CIは`--cov`付きでpytestを実行する。

#5で、テストで作ったアプリのエンジンを、テストの後で`dispose()`するように直した（8章）。

1〜7章は、修正前の状態の説明。

## 1. 現象

CI（`.github/workflows/ci.yml`のRun tests）のwarnings summaryには、次のような警告が並ぶ。

## 2. テストのDBとエンジン

### `src/fl_demonstro/config.py:225`

```python

```

- `TestingConfig`のDBはin-memoryのSQLite。\
  ファイルを作らず、接続（`sqlite3.Connection`）の中にだけDBがある。\
  接続を閉じるとDBも消える。

### `flask_sqlalchemy/extension.py:610-616`

```python
if url.database is None or url.database in {"", ":memory:"}:
    options["poolclass"] = sa.pool.StaticPool

    if "connect_args" not in options:
        options["connect_args"] = {}

    options["connect_args"]["check_same_thread"] = False
```

- Flask-SQLAlchemyは、in-memoryのSQLiteには`StaticPool`を使う。
- エンジン・プール・接続の関係は次のとおり。
  - エンジン（`Engine`）：DBへの入口。プールを1つ持つ。
  - プール（`Pool`）：接続を作り、使い回す。
  - 接続：DBAPIの接続。SQLiteなら`sqlite3.Connection`。
- `StaticPool`は接続を1本だけ作り、すべてのリクエストで同じ接続を使う。\
  in-memoryのDBは接続を閉じると消えるので、プールが接続を持ち続ける必要がある。
- `check_same_thread=False`は、別のスレッドからも同じ接続を使えるようにする設定。

### `flask_sqlalchemy/extension.py:273-274`・`359`

```python
self._app_engines = WeakKeyDictionary()
```

```python
engines = self._app_engines.setdefault(app, {})
```

- エンジンはアプリごとに作られ、`db._app_engines`に入る。
- `WeakKeyDictionary`はキー（アプリ）を弱参照で持つ。\
  アプリが回収されると、そのエントリは自動で消える。
- 値（エンジンのdict）は普通の参照で持つ。\
  アプリが生きている間は、エンジンもこのエントリから参照され続ける。

## 4. 接続が捨てられるまで

### 参照カウントとGC

CPythonはオブジェクトを2つの仕組みで回収する。

- **参照カウント**：オブジェクトを指す参照が0になった時点で、すぐに回収する。
- **循環参照のGC**：A → B → Aのように互いを指すオブジェクトは、外から指されなくても参照が0にならない。\
  これを見つけて回収するのがGC（`gc`モジュール）。\
  オブジェクトを作った数が閾値を超えると自動で走る。`gc.collect()`で明示的に走らせることもできる。

### アプリとエンジンは循環参照を含む

アプリは循環参照を含むので、テストが終わって参照がなくなっても、GCが走るまで残る。

エンジンも循環参照を含む。

`gc.get_referrers()`で調べると、次の2つが見つかった。

#### `sqlalchemy/engine/base.py:2967-2970`

```python
if query_cache_size != 0:
    self._compiled_cache = util.LRUCache(
        query_cache_size, size_alert=self._lru_size_alert
    )
```

- エンジン → `_compiled_cache`（`LRUCache`）→ `_lru_size_alert`（エンジンのバウンドメソッド）→ エンジン、と一周する。

#### `sqlalchemy/engine/create.py:731-736`・`776-778`

```python
def first_connect(
    dbapi_connection, connection_record
) -> None:
    c = base.Connection(engine, ...)
```

```python
event.listen(
    pool,
    "connect",
    first_connect,
    _once_unless_exception=True,
)
```

（型ヒントと引数の一部は省略）

- `first_connect`は`create_engine()`の中のクロージャで、外側の`engine`を参照している。
- エンジン → プール → イベントのリスナー（`first_connect`）→ エンジン、と一周する。

### GCが2回必要になる

アプリへの参照がなくなってから接続が捨てられるまでに、GCが2回走る必要がある。

1. **1回目のGCでアプリが回収される**：アプリが消えるので、`db._app_engines`のエントリも消える。\
   エンジンを指していたのはこのエントリなので、ここでエンジンが不要になる。\
   ただし、エントリが消えるのは今回のGCで回収するものが決まった後なので、エンジンは今回の対象に入らない。
2. **2回目のGCでエンジンが回収される**：エンジン・プール・接続がまとめて回収される。\
   このとき`sqlite3.Connection`が`close()`されないまま回収され、`ResourceWarning`が出る。

### 実験

```python
import gc
import warnings
import weakref

from fl_demonstro import create_app
from fl_demonstro.config import TestingConfig
from fl_demonstro.extensions import db

warnings.simplefilter("default", ResourceWarning)

app = create_app(TestingConfig)
with app.app_context():
    db.create_all()
    engine = weakref.ref(db.engine)
app = weakref.ref(app)

print("1回目")
gc.collect()
print(app(), engine())

print("2回目")
gc.collect()
print(app(), engine())
```

- `weakref.ref()`は弱参照で、回収を妨げずに「まだ生きているか」を確かめられる（回収済みなら`None`を返す）。
- `app = weakref.ref(app)`で、アプリへの普通の参照をなくしている。

実行結果は次のとおり。

```text
1回目
None Engine(sqlite:///%3Amemory%3A)
2回目
.../doc_exp.py:27: ResourceWarning: unclosed database in
  <sqlite3.Connection object at 0x76555ca218c0>
None None
```

（警告は標準エラーに出るので、実際の表示順は前後する）

- 1回目の`gc.collect()`の後は、アプリだけが消え、エンジンは残っている。
- 2回目の`gc.collect()`（27行目）でエンジンが消え、警告が出る。

### Python 3.13からの警告

Python 3.13から、`sqlite3.Connection`は`close()`されないまま回収されると`ResourceWarning`を出すようになった。

ファイルやソケットが閉じられずに回収されたときと同じ扱いで、リソースの閉じ忘れを知らせるための警告。

## 5. 警告が出る場所と件数

### 関係のないテストの場所として出る

警告は、GCが走ったときに動いていたコードの場所として出る。

GCはオブジェクトを作った数で自動的に走るので、どこで走るかは決まっていない。

CIでは、次のような場所として出ていた。

- `jinja2/nodes.py`・`jinja2/visitor.py`（テンプレートのコンパイル）
- `sqlalchemy/engine/result.py`・`sqlalchemy/sql/type_api.py`（クエリの結果の処理）
- `configparser.py`（`test_migrations.py`がAlembicの設定を読むところ）

テストの名前も、`test_passwords.py`・`test_auth.py`・`test_session.py`など、警告の原因と関係のないものになる。

### summaryに入らない警告

#### `_pytest/unraisableexception.py:27-29`

```python
def gc_collect_harder(iterations: int) -> None:
    for _ in range(iterations):
        gc.collect()
```

- pytestは終了処理（`pytest_unconfigure`）で、この関数を通して`gc.collect()`を1回呼ぶ（CPythonの場合）。
- このとき回収されたエンジンの警告は、summaryを出した後なので、件数に入らず標準エラーに出る（CIの59件）。
- このGCで回収された最後のアプリのエンジンは、もう1回のGCを待つ。\
  インタプリタの終了時に回収され、`<sys>:0: ResourceWarning`と出る（CIの1件）。

### 件数が変わる理由

GCが走るタイミングは、作ったオブジェクトの数で決まる。

coverageの有無やPythonのパッチバージョンなどで数が変わると、テストの実行中に回収される分（summaryの件数）と、終了処理で回収される分の割合も変わる。

## 6. 手元で見えない理由

### Pythonのデフォルトの警告フィルタ

`warnings.filters`の初期値は次の5つ。

- `default::DeprecationWarning:__main__`
- `ignore::DeprecationWarning`
- `ignore::PendingDeprecationWarning`
- `ignore::ImportWarning`
- `ignore::ResourceWarning`

`ResourceWarning`はignoreされるので、何も設定しなければ表示されない。

### `_pytest/config/__init__.py:1328-1332`

```python
with warnings.catch_warnings(record=record) as log:
    if not sys.warnoptions:
        warnings.filterwarnings(
            "always", category=DeprecationWarning
        )
        warnings.filterwarnings(
            "always", category=PendingDeprecationWarning
        )
```

- pytestはテストごとにこのフィルタで警告を記録し、warnings summaryに出す。
- pytestが表示に切り替えるのは`DeprecationWarning`と`PendingDeprecationWarning`だけで、`ResourceWarning`はignoreのまま。

### `pytest_cov/plugin.py:330-334`

```python
for _, message, category, _, _ in warnings.filters:
    if category is ResourceWarning and message in (
        COVERAGE_SQLITE_WARNING_RE,
        COVERAGE_SQLITE_WARNING_RE2,
    ):
        break
else:
    warnings.filterwarnings(
        "default",
        "unclosed database in"
        " <sqlite3.Connection"
        " object at",
        ResourceWarning,
    )
```

- pytest-covは`--cov`のとき、`pytest_runtestloop`でこのフィルタを足す。
- 目的は、coverage自身の警告を扱うこと。\
  coverageは計測データをSQLiteのファイル（`.coverage`）に保存するので、同じ警告を出すことがある。\
  `filterwarnings = ["error"]`のような厳しい設定でも、それがエラーにならないように`default`にしている。
- `filterwarnings()`の第2引数は、警告メッセージの先頭にマッチする正規表現。\
  アプリの接続の警告も同じメッセージで始まるので、このフィルタに当たって表示される。
- `default`は「同じ場所・同じメッセージの警告は1回だけ表示する」。\
  メッセージにはアドレス（`0x...`）が入って毎回違うので、実際にはすべて表示される。

### `.github/workflows/ci.yml:63-67`

```yaml

  --cov=src \
  --cov-report=term-missing \
```

（レポートの出力先は省略）

## 7. 影響

- テストだけの問題。\

## 8. 直し方（#5）

テストで作ったアプリのエンジンを、テストの終わりに`dispose()`するようにした。

### `tests/conftest.py`

```python
MakeApp = Callable[[type[Config]], Flask]


@pytest.fixture
def make_app() -> Iterator[MakeApp]:
    apps: list[Flask] = []

    def _make_app(config_class: type[Config]) -> Flask:
        app = create_app(config_class)
        with app.app_context():
            db.create_all()
        apps.append(app)
        return app

    yield _make_app

    for app in apps:
        with app.app_context():
            db.session.remove()
            db.drop_all()
            db.engine.dispose()


@pytest.fixture
def app(make_app: MakeApp) -> Flask:
    return make_app(TestingConfig)
```

（コメントとdocstringは省略）

- `make_app`を、ただの関数からフィクスチャに変えた。\
  このフィクスチャは、アプリを作る関数（`_make_app`）を返す。\
  pytestで「factoryをフィクスチャにする」と呼ばれる書き方。
- 作ったアプリを`apps`に記録し、`yield`の後（テストの後片付け）でまとめて`db.engine.dispose()`する。\
  1つのテストで複数のアプリを作っても、すべて片付けられる。
- `app`フィクスチャも`make_app`を使うので、片付けは`make_app`の1か所にまとまる。
- `MakeApp`は、`make_app`が返す関数の型（設定クラスを受け取り、アプリを返す）。\
  テストの引数の型注釈に使う。

### テスト側

```python
from tests.conftest import MakeApp


def test_signup_is_rate_limited(make_app: MakeApp) -> None:
    client = make_app(RateLimitEnabledConfig).test_client()
```

（`tests/test_security.py`から抜粋）

- 3章の4つのファイルのテストは、`make_app`をimportせず、フィクスチャとして引数で受け取るようにした。
- ヘルパー（`_rate_limited_app_with_user()`・`_victim_with_remember_cookie_and_planted_session()`）は、`make_app`を引数で受け取る。
- `create_app()`を直接呼ぶテスト（`test_config.py`、`test_session.py`のセッションの保存先のテスト）は、DBに接続しないのでそのまま。

### 確認したこと

- 修正後は、`-W default::ResourceWarning`でも`--cov=src`でも、SQLiteの警告はsummary・標準エラーとも0件。
- 修正前に`-W default::ResourceWarning`でsummaryに出た57件のうち、55件は`app`フィクスチャ、残りはテストの中で直接`make_app()`したアプリの接続だった（`PYTHONTRACEMALLOC`で作成元を確かめた）。

### 修正前の実験：すべてのエンジンをdisposeする

直し方を決める前に、作られたエンジンを記録し、各テストの後で`dispose()`するpytestプラグインを一時的に読み込んだ（リポジトリには入れていない）。

```python
import pytest
from flask_sqlalchemy import SQLAlchemy

engines = []
make_engine = SQLAlchemy._make_engine


def record(self, *args):
    engine = make_engine(self, *args)
    engines.append(engine)
    return engine


SQLAlchemy._make_engine = record


@pytest.hookimpl(wrapper=True)
def pytest_runtest_teardown(item):
    result = yield
    while engines:
        engines.pop().dispose()
    return result
```

- `-W default::ResourceWarning`でも`--cov=src`でも、SQLiteの警告はsummary・標準エラーとも0件になった。
- これで`dispose()`すれば警告が消えることを確かめた。\
  ただし`_make_engine`はFlask-SQLAlchemyの内部のメソッドなので、修正にはこの方法を使わず、`make_app`フィクスチャで片付けるようにした。

### これからテストを書くとき

DBに接続するアプリは、`create_app()`を直接呼ばず、`make_app`フィクスチャで作る。

`create_app()`で作ると、エンジンが`dispose()`されず、また接続がGC任せになる。
