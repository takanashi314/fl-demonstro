# docker compose up --buildの流れD：コンテナを作り、起動の順番を決める（6D）

`docs/06.md`のD（34〜38）を詳しくしたもの。

コードやログは、iPhoneの縦画面で読めるよう、改行やインデントを変えたり、一部を省いたりしている。

出力は、2026-11-27に手元で実行して取ったもの（Docker 29.7.2、Compose v5.5.0）。ログの時刻はUTC（日本時間の9時間前）。

## 全体像

Dは、Composeがコンテナを作り（create）、依存の順に起動する（start）段階。

Dockerのイベント（`docker events`）を、時刻の順に並べると次のようになる。

```text
21:30:57.682 network create fl-demonstro_default
21:30:57.769 container create fl-demonstro-redis-1
21:30:57.840 container create fl-demonstro-web-1
21:30:57.844 container attach fl-demonstro-redis-1
21:30:57.845 container attach fl-demonstro-web-1
21:30:57.859 volume mount fl-demonstro_redis-data
21:30:58.045 network connect fl-demonstro_default
21:30:58.081 container start fl-demonstro-redis-1
21:30:58.094 volume mount fl-demonstro_db-data
21:30:58.341 network connect fl-demonstro_default
21:30:58.371 container start fl-demonstro-web-1
```

（イベントの時刻は、Dockerがイベントを出した時刻。処理そのものの時刻より少し遅れる）

- 2つとも先に作ってから、redis → webの順に起動する（3章）。
- ボリュームを付けるのも、ネットワークにつないでIPアドレスを割り当てるのも、作るときではなく起動するとき（4章）。

## 1. 作るか、そのまま使うか

1. Composeは、ラベル（`com.docker.compose.project=fl-demonstro`・`com.docker.compose.service=web`など）で、このプロジェクトのコンテナを探す。
2. なければ作る（`Created`）。
3. あれば、コンテナのラベルの2つの値を、今の設定と比べる。
   - `com.docker.compose.config-hash`：サービスの設定（`docker compose config`で見える、解釈した後の形）から計算したハッシュ。
   - `com.docker.compose.image`：コンテナを作ったときのイメージのID。

```text
$ docker compose config --hash '*'
redis 738202516ad5a8796ba46b...
web bc37f21f6de847375d69ad...

$ docker inspect -f '{{index .Config.Labels
    "com.docker.compose.config-hash"}}' \
    fl-demonstro-web-1
bc37f21f6de847375d69ad...
```

4. どちらも同じなら作り直さず、止まっていれば起動し、動いていれば何もしない。\
   どちらかが違えば、作り直す（古いコンテナを止めて消し、新しく作る）。

```text
（止まったコンテナがあるとき）
 Container fl-demonstro-redis-1 Started
 Container fl-demonstro-web-1 Started

（動いているとき）
 Container fl-demonstro-redis-1 Running
 Container fl-demonstro-web-1 Running

（--force-recreateを付けたとき）
 Container fl-demonstro-redis-1 Recreated
 Container fl-demonstro-web-1 Recreated
```

（`Starting`・`Recreate`などの途中の行は省いている）

5. 作り直しになる例。
   - コードを変えて`--build`：イメージのIDが変わるので、webだけを作り直す。コードを変えずに`--build`しても、イメージのIDは同じ（`docs/6B.md`の25）なので、`Running`のまま。
   - `.env`の`SECRET_KEY`を変える：`environment:`の値が変わり、config-hashが変わる。
   - `compose.yaml`のwebの`ports`などを変える。
   - `compose.yaml`のコメントだけを変える：解釈した後の設定は同じなので、config-hashは変わらない。
6. 作り直すと、コンテナの中で書いたファイルは消える（gunicornの管理用ソケット`/home/app/.gunicorn/gunicorn.ctl`など）。\
   ボリュームは新しいコンテナに付け直されるので、DBとRedisのデータは残る。

## 2. コンテナの設定

7. 名前は`<プロジェクト名>-<サービス名>-<番号>`。\
   番号はラベルの`com.docker.compose.container-number`で、1つのサービスのコンテナを増やすと（`--scale web=2`）、2・3…になる。
8. Composeが作ったwebのコンテナ（`docker inspect`の一部）：

```json
{
 "Path": "entrypoint.sh",
 "Args": ["gunicorn", "--bind", "0.0.0.0:8000",
          "--workers", "2", "--access-logfile", "-",
          "fl_demonstro:create_app()"],
 "Config": {
  "User": "app",
  "WorkingDir": "/app",
  "Hostname": "128b36ee3028",
  "Env": [
   "SECRET_KEY=（省略）",
   "REDIS_URL=redis://redis:6379/0",
   "SESSION_COOKIE_SECURE=false",
   "PATH=/app/.venv/bin:/usr/local/bin:...",
   "LANG=C.UTF-8",
   "（イメージのEnvが続く）"
  ]
 },
 "HostConfig": {
  "PortBindings": {
   "8000/tcp": [{"HostIp": "127.0.0.1",
                 "HostPort": "8000"}]
  },
  "RestartPolicy": {"Name": "unless-stopped",
                    "MaximumRetryCount": 0},
  "NetworkMode": "fl-demonstro_default",
  "LogConfig": {"Type": "json-file", "Config": {}}
 },
 "Mounts": [{
  "Type": "volume",
  "Name": "fl-demonstro_db-data",
  "Destination": "/app/instance",
  "RW": true
 }]
}
```

9. `Path`・`Args`：イメージの`Entrypoint`と`Cmd`をそのまま使う（webは`compose.yaml`で上書きしていない）。\
   redisは`command:`が`Cmd`を置き換えるので、`Path`がイメージの`docker-entrypoint.sh`、`Args`が`redis-server --appendonly yes ...`になる。
10. `Env`：`compose.yaml`の`environment:`の3つが先に、イメージの`Env`が後に並ぶ。\
    同じ名前があれば、`environment:`の値だけが残る。\
    `SECRET_KEY`の値も`docker inspect`にそのまま出るので、この出力を人に見せるときは注意する。
11. `User`：イメージの`USER`（`app`）。redisは空で、rootで起動する。
12. `Hostname`：コンテナIDの先頭12文字。
13. `RestartPolicy`：`unless-stopped`。`MaximumRetryCount`は`on-failure`のときだけ使う値。
14. `LogConfig`：Dockerの既定の`json-file`。オプションを付けていないので、ログのファイルは大きくなり続ける（`docs/6I.md`の1章）。
15. ラベルは、1章の2つのほかに次のものがある。
    - `com.docker.compose.depends_on`：`redis:service_started:false`（サービス名:条件:`restart`の値）。
    - `com.docker.compose.project.config_files`・`com.docker.compose.project.working_dir`：`compose.yaml`とプロジェクトのフォルダの絶対パス。
    - `com.docker.compose.oneoff`：`False`（`docker compose run`で作った使い捨てのコンテナは`True`）。
16. 書いていないので、Dockerの既定値になるもの。
    - `Init`：なし。tiniのような小さなinitを挟まないので、`entrypoint.sh`がそのままPID 1になる（`docs/6F.md`の1章）。
    - `StopSignal`：なし（SIGTERM）。`StopTimeout`：なし（10秒）。どちらも止めるときに使う（`docs/6I.md`の2章）。
    - `CapAdd`・`CapDrop`：なし。Dockerの既定の14個のcapabilitiesが上限になる（webの中の`/proc/1/status`の`CapBnd: 00000000a80425fb`）。webのプロセスはrootではないので、実際に持っているのは0個（`CapEff: 0000000000000000`）。
    - `Ulimits`：なし。開けるファイルの数は、ソフト1024・ハード1048576（webの中の`ulimit -n`・`ulimit -Hn`）。
    - seccomp：Dockerの組み込みのプロファイル（`docker info`の`SecurityOptions`の`name=seccomp,profile=builtin`）。
    - 標準入力：つながない（`stdin_open:`がないので、PID 1の標準入力は`/dev/null`）。

## 3. 作る順番と、起動の順番

17. 作るのも起動するのも、依存の順（redis → web）。\
    2つとも作り終えてから、起動を始める。
18. `-d`を付けない`up`では、起動する前に、2つのコンテナの出力につなぐ（イベントの`attach`）。\
    起動した直後の出力も取りこぼさないため。Composeの`Attaching to redis-1, web-1`は、このときに出る。
19. `depends_on`の短い書き方は`condition: service_started`（`docs/6A.md`の18）。\
    Composeは、redisの起動（Dockerの`start`の呼び出し）が終わるのを待ってから、webを起動する。\
    `start`は、コンテナのプロセスを作ったところで戻るので、Redisの準備ができたかは見ていない。
20. 今回の時刻：

```text
21:30:57.872 redisのプロセスが起動
21:30:58.111 webのプロセスが起動
21:30:58.193 Redisが接続を受け付け始める
```

（上の2つは`docker inspect`の`State.StartedAt`、3つ目はRedisのログ）

webは、Redisが接続を受け付け始める80ミリ秒前に起動していた。

21. それでも困らないのは、起動のときにはRedisにつながないから。\
    `flask db upgrade`の`create_app()`も、gunicornのワーカーの`create_app()`も、Redisのクライアント（接続プール）を作るだけで、最初のコマンドを送るまではつながない（`docs/6H.md`の4章）。
22. 待たせたいときは、redisに`healthcheck:`（`redis-cli ping`など）を書き、webの`depends_on`を`condition: service_healthy`にする。
23. `depends_on`が効くのは、Composeが起動するときだけ。\
    `restart: unless-stopped`でDockerが起動し直すとき（`docs/6F.md`の2章）は、依存の順を見ない。

## 4. 起動するときに、ネットワークにつなぐ

24. ネットワークにつなぐのは起動するときで（イベントの`network connect`は`start`の直前）、IPアドレスもこのときに割り当てられる。
25. 先に起動したredisが172.18.0.2、webが172.18.0.3になった（172.18.0.1はゲートウェイ。`docs/6C.md`の5）。\
    起動の順やほかのコンテナによって変わるので、アプリでは名前を使う。
26. DockerのDNSに、サービス名・コンテナ名・コンテナIDの先頭12文字が登録される。

```text
"DNSNames": [
  "fl-demonstro-web-1",
  "web",
  "128b36ee3028"
]
```

（`docker inspect`の`NetworkSettings.Networks`の一部）

27. コンテナの`/etc/resolv.conf`は、DockerのDNS（127.0.0.11）を指すように書き換えられる。

```text
# webの中の/etc/resolv.conf（一部）
nameserver 127.0.0.11
options ndots:0

# Based on host file: '/etc/resolv.conf'
#   (internal resolver)
# ExtServers: [host(10.255.255.254)]
```

28. 127.0.0.11はコンテナの中のアドレスだが、答えるのはdockerd。\
    同じネットワークの名前（`redis`・`web`など）はdockerdが答え、それ以外（`pypi.org`など）は`ExtServers`（WSLのDNS）に問い合わせる。

```text
$ getent hosts redis web fl-demonstro-redis-1
172.18.0.2      redis
172.18.0.3      web
172.18.0.2      fl-demonstro-redis-1
```

（webの中で実行）

29. `options ndots:0`：ドットのない名前でも、検索ドメインを付けずに、まずそのまま問い合わせる。
30. `/etc/hosts`には、自分のホスト名（コンテナID）とアドレスだけが書かれ、ほかのコンテナの名前は書かれない。\
    名前は接続を作るたびにDNSで引くので、redisを作り直してアドレスが変わっても、新しく作る接続は新しいアドレスに向かう。

## 5. 起動するときに、ポートをつなぐ

31. webを起動するとき、dockerdがWSLの127.0.0.1:8000で待ち受けるソケットを作り、docker-proxyというプロセスを起動して渡す。

```text
/usr/bin/docker-proxy -proto tcp
  -host-ip 127.0.0.1 -host-port 8000
  -container-ip 172.18.0.3 -container-port 8000
  -use-listen-fd
```

（WSLの`ps`で見たもの）

32. `-use-listen-fd`：待ち受けのソケットはdockerdが作り、ファイルディスクリプタとしてdocker-proxyに渡す。\
    ポートがほかのプロセスに使われていれば、この時点でwebの起動はエラーになる。
33. `-container-ip`を渡すので、ネットワークにつないでアドレスが決まった後（24）でないと、ポートはつなげない。
34. docker-proxyは、来た接続ごとに、コンテナの172.18.0.3:8000へ新しい接続を作って中継する（`docs/6H.md`の1章）。\
    iptablesの規則も足されるが、見るにはroot権限が要るので、ここでは確かめていない。

## 6. 起動した後

35. コンテナごとに`containerd-shim-runc-v2`というプロセスが1つずつ起動し、コンテナのPID 1の親になる。\
    shimが、PID 1の終了（終了ステータス）や出力を受け取り、containerdとdockerdに伝える。
36. コンテナのプロセスの標準出力と標準エラーは、shimを通してdockerdに送られ、ログのファイルに書かれる（`docs/6I.md`の1章）。
37. この先は、redisがE（`docs/6E.md`）、webがF（`docs/6F.md`）に進む。
