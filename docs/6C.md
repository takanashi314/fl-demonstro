# docker compose up --buildの流れC：ネットワークとボリュームを作る（6C）

`docs/06.md`のC（32〜33）を詳しくしたもの。

コードやログは、iPhoneの縦画面で読めるよう、改行やインデントを変えたり、一部を省いたりしている。

出力は、2026-11-27に手元で実行して取ったもの（Docker 29.7.2、Compose v5.5.0）。

## 全体像

Cの段階で用意するのは、2つのコンテナがつながるネットワーク1つと、データを置くボリューム2つ。\
どちらもコンテナより先に用意し、コンテナより長く残る（ネットワークは`down`まで、ボリュームは`down -v`まで）。

Composeは、作る前に同じ名前のものがあるかを確かめ、あればそのまま使う。

```text
（ボリュームが残っているとき：今回）
 Network fl-demonstro_default Created

（ボリュームがないとき：別のプロジェクト名で試した）
 Network fl-demonstro-docs_default Created
 Volume fl-demonstro-docs_redis-data Created
 Volume fl-demonstro-docs_db-data Created
```

（`Creating`の行は省いている）

ネットワークは2回目以降の`up`でも、`down`した後なら作り直される。\
ボリュームは最初の`up`で作ったものが残り続けるので、ふだんの出力には出てこない。

## 1. ネットワーク

1. 名前は`fl-demonstro_default`（`docs/6A.md`の4章）。\
   `compose.yaml`に`networks:`を書いていないので、Composeが`default`という名前のネットワークを1つ用意し、全サービスをつなぐ。
2. 同じ名前のネットワークがなければ、`bridge`ドライバーで作る。\
   あれば、ラベル（10）がこのプロジェクトのものかを確かめて、そのまま使う。
3. 作られたネットワーク（`docker network inspect`の一部）：

```json
{
 "Name": "fl-demonstro_default",
 "Driver": "bridge",
 "EnableIPv6": false,
 "IPAM": {
  "Driver": "default",
  "Config": [{"Subnet": "172.18.0.0/16",
              "Gateway": "172.18.0.1"}]
 },
 "Internal": false,
 "Labels": {
  "com.docker.compose.config-hash": "8b4b7a70...",
  "com.docker.compose.network": "default",
  "com.docker.compose.project": "fl-demonstro",
  "com.docker.compose.version": "5.5.0"
 }
}
```

4. サブネットは、Dockerが持っている範囲（default-address-pools）から、空いている/16を1つ選ぶ。\
   172.17.0.0/16はDocker自身の`bridge`ネットワークが使っているので、次の172.18.0.0/16になった。\
   ほかにネットワークがあれば172.19.0.0/16などになるので、アドレスを決め打ちしてはいけない。
5. ゲートウェイの172.18.0.1は、Dockerが動いているマシン（今回はWSL）に作られるLinuxのブリッジ`br-<ネットワークIDの先頭12文字>`のアドレス。

```text
$ ip -br addr show br-bd014c9b4edf
br-bd014c9b4edf  UP  172.18.0.1/16 fe80::.../64
```

（別のプロジェクト名で作ったネットワークで確かめた）

6. コンテナは、起動するときに、仮想のケーブル（vethのペア）でこのブリッジにつながる（`docs/6D.md`の4章）。\
   ブリッジは、つながったコンテナ同士の通信を中継するスイッチの役割をする。
7. ブリッジにアドレスがあるので、WSL自身からもコンテナのアドレスに直接つながる。\
   `ports`を書いていないRedisにも、WSLからは172.18.0.2:6379でつながった（`docs/6E.md`の4章）。\
   ほかのマシン（同じネットワークのスマートフォンなど）からは、このアドレスに届かない。
8. `Internal: false`なので、コンテナから外（インターネット）にも出られる。\
   外へ出る通信は、送り元をマシンのアドレスに付け替えて（NAT）出ていく。
9. Composeが作るネットワークは、自分で作ったネットワーク（user-defined network）の扱いになり、DockerのDNSでサービス名を引ける（`docs/6D.md`の4章）。\
   Dockerが最初から持っている`bridge`ネットワークでは、名前は引けない。
10. ラベルは、Composeが後で自分のプロジェクトのものを見分けるのに使う。\
    `config-hash`はネットワークの設定から計算した値で、設定が変わったかどうかの判断に使う。
11. ネットワークは`docker compose stop`では消えず、`docker compose down`で消える（`docs/6I.md`の5章）。

## 2. ボリューム

12. 名前は`fl-demonstro_db-data`と`fl-demonstro_redis-data`。
13. 同じ名前のボリュームがあれば、何も出さずにそのまま使い、中身にも触らない。\
    今回は11-21の最初の`up`で作ったものが残っていた（下の`CreatedAt`）。
14. なければ、`local`ドライバーで作る。

```json
{
  "CreatedAt": "2026-11-21T17:07:07+09:00",
  "Driver": "local",
  "Labels": {
    "com.docker.compose.config-hash": "1192f19d...",
    "com.docker.compose.project": "fl-demonstro",
    "com.docker.compose.version": "5.5.0",
    "com.docker.compose.volume": "db-data"
  },
  "Mountpoint":
    "/var/lib/docker/volumes/fl-demonstro_db-data/_data",
  "Name": "fl-demonstro_db-data",
  "Options": null,
  "Scope": "local"
}
```

15. 中身の実体は、Dockerが動いているマシンの`Mountpoint`のフォルダ。\
    rootでないと入れない場所なので、中を見るときは、ボリュームを付けた別のコンテナを使う（`docker run --rm -v fl-demonstro_redis-data:/data:ro alpine ls /data`など）。
16. 同じ名前で、Composeのラベルがないボリューム（`docker volume create`で自分で作ったものなど）があると、Composeは警告を出してから、そのまま使う。\
    Composeの外で管理するボリュームを使うなら、`compose.yaml`のトップレベルの`volumes:`に`external: true`と書く。
17. 作ったばかりのボリュームは空。\
    最初にコンテナに付けたときに、イメージのその場所の中身と所有者がコピーされる（`docs/6E.md`の1章・`docs/6F.md`の1章）。
18. 作るのは、起動するサービスが使うボリュームだけ。\
    `docker compose up -d redis`のようにサービスを指定すると、`redis-data`だけが作られる。
19. ボリュームは`docker compose down`でも消えない。\
    消えるのは`down -v`か`docker volume rm`のとき（`docs/6I.md`の5章）。\
    コンテナを作り直しても、DB（`app.db`）とRedisのデータ（AOF）が残るのはこのため。

## 3. バインドマウントではなく名前付きボリュームを使う理由

`volumes:`には、手元のフォルダをそのまま付ける書き方（バインドマウント。`./instance:/app/instance`など）もある。\
このプロジェクトが名前付きボリュームを使っているのは、次の違いがあるから。

20. 所有者：名前付きボリュームは、空のときにイメージの所有者（`app:app`）がコピーされる（17）。\
    バインドマウントは手元のフォルダの所有者のままなので、uid 999の`app`ユーザーが書き込めないことがある。
21. 中身の分離：バインドマウントだと、手元で`flask run`したときの`instance/app.db`とコンテナのDBが同じファイルになる。\
    名前付きボリュームなら、手元の`instance/`とは別になる。
22. 後片付け：Composeが作ったものとしてラベルが付き、`down -v`でまとめて消せる。
