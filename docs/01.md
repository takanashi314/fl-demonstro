# Redisへの書き込みの解説（01）

コードの抜粋は、iPhoneの縦画面で読めるよう、元のファイルから改行やインデントを変えている（中身は同じ）。

## 全体像

アプリのコードはRedisを直接操作していない（`set`や`incr`を自分で呼んでいない）。

Redisに書き込むのは次の2つの拡張機能で、アプリ側がやっているのは「どのRedisを使うか」の設定だけ。

- **セッション**
  - 書き込むライブラリ：Flask-Session
  - キー：`session:<セッション ID>`
  - 値：セッションのdict（msgpack）
  - TTL：`PERMANENT_SESSION_LIFETIME`（12時間）
- **回数制限**
  - 書き込むライブラリ：Flask-Limiter（中身は`limits`）
  - キー：`LIMITS:LIMITER/<識別子>/<エンドポイント>/<回数>/<1>/<単位>`
  - 値：回数（整数）
  - TTL：制限の期間（60秒・3600秒）

どちらも同じRedisのDB 0を使い、キーの接頭辞（`session:` / `LIMITS:`）で分かれている。

Redisクライアントは別々で、セッションはアプリが作った`Redis`オブジェクト、回数制限は`limits`がURIから自分で作る接続を使う。

Redisを使う理由は、本番（Docker）のgunicornが`--workers 2`で動くため。

回数制限を`memory://`にすると記録がワーカー（プロセス）ごとに別になり、制限が実質2倍に緩む。

## 2. セッションの保存先を選ぶ

### `src/fl_demonstro/__init__.py:34-45`

```python
def _configure_session_storage(app: Flask) -> None:
    """セッションの保存先を決める（設定で指定されていればそれを使う）。"""
    if app.config.get("SESSION_TYPE"):
        return
    if redis_url := app.config.get("REDIS_URL"):
        app.config["SESSION_TYPE"] = "redis"
        app.config["SESSION_REDIS"] = Redis.from_url(
            redis_url
        )
    else:
        app.config["SESSION_TYPE"] = "cachelib"
        app.config["SESSION_CACHELIB"] = FileSystemCache(
            str(Path(app.instance_path) / "sessions"),
            threshold=1000,
        )
```

- `SESSION_TYPE = "redis"`と`SESSION_REDIS`（Redisクライアント）をconfigに入れておくと、Flask-Sessionがそれを読んで`RedisSessionInterface`を`app.session_interface`に設定する。
- `Redis.from_url()`はクライアント（コネクションプール）を作るだけで、この時点では接続しない。\
  最初のコマンドで初めて接続するので、Redisが止まっていても`create_app()`は成功する。
- `tests/test_session.py`の`test_session_storage_is_chosen_from_redis_url`は、この選び分けを確認している（接続しないのでRedisがなくても通る）。

## 3. Flask-SessionがRedisに書き込む処理（ライブラリ側）

実際に`SET` / `GET` / `DEL`を呼んでいるのは`RedisSessionInterface`。

いつ呼ぶかは、共通の基底クラス`ServerSideSessionInterface`が決めている。

### `.venv/.../flask_session/redis/redis.py:62-85`

```python
def _retrieve_session_data(
    self, store_id: str
) -> Optional[dict]:
    # Get the saved session (value)
    # from the database
    serialized_session_data = self.client.get(store_id)
    if serialized_session_data:
        return self.serializer.decode(
            serialized_session_data
        )
    return None


def _delete_session(self, store_id: str) -> None:
    self.client.delete(store_id)


def _upsert_session(
    self,
    session_lifetime: TimeDelta,
    session: ServerSideSession,
    store_id: str,
) -> None:
    storage_time_to_live = total_seconds(session_lifetime)

    # Serialize the session data
    serialized_session_data = self.serializer.encode(
        session
    )

    # Update existing or create new
    # session in the database
    self.client.set(
        name=store_id,
        value=serialized_session_data,
        ex=storage_time_to_live,
    )
```

- キー（`store_id`）は`key_prefix + sid`、つまり`session:` +セッションID。\
  セッションIDは`secrets.token_urlsafe(32)`（43文字）。
- 値はmsgspecのmsgpackでシリアライズしたdict。
- `SET ... EX 43200`なので、Redis側のTTLで古いセッションが自動で消える（ファイル保存のような掃除が要らない）。
- ブラウザのCookieに入るのはセッションIDだけで、中身はサーバー側にしかない。

### `.venv/.../flask_session/base.py:274-305`（抜粋）

リクエストの最後にFlaskが呼ぶ`save_session()`。

```python
def save_session(self, app, session, response) -> None:
    ...
    store_id = self._get_store_id(session.sid)
    ...
    # If the session is empty, do not
    # save it to the database or set
    # a cookie
    if not session:
        # If the session was deleted
        # (empty and modified), delete
        # the saved session ...
        if session.modified:
            self._delete_session(store_id)
            response.delete_cookie(
                key=name, domain=domain, path=path
            )
            response.vary.add("Cookie")
        return

    if not self.should_set_storage(app, session):
        return

    self._upsert_session(
        app.permanent_session_lifetime, session, store_id
    )
```

- セッションが空ならRedisに書かない。\
  未ログインでトップページを見るだけでは、キーは作られない。
- ログイン画面を開くとCSRFトークンがセッションに入るので、ログインしていなくてもキーが1つ作られる。\
  compose.yamlで`maxmemory`を付けている理由がこれ（7章）。

### `.venv/.../flask_session/base.py:221-232`（docstring省略）

```python
def should_set_storage(
    self, app: Flask, session: ServerSideSession
) -> bool:
    return (
        session.modified
        or app.config["SESSION_REFRESH_EACH_REQUEST"]
    )
```

- Flaskの`SESSION_REFRESH_EACH_REQUEST`は既定で`True`。\
  そのため、中身のあるセッションはリクエストのたびに`SET`され直し、TTLが12時間に戻る。\
  configのコメント「操作がなければ12時間で期限切れ」はこの動きのこと。

## 4. アプリ側でセッションIDを作り直す

アプリのコードでRedisの中身に影響するのは、セッションIDの作り直しだけ。

### `src/fl_demonstro/accounts/views.py:38-47`

```python
def _regenerate_session_id() -> None:
    """セッション ID を新しくし、
    古い ID のセッションをサーバーから消す。

    Flask-Session の regenerate() は中身が空のセッションでは何もしないので、
    セッションに値を書いたあと（login_user() や flash() のあと）に呼ぶこと。
    """
    regenerate = getattr(
        current_app.session_interface, "regenerate", None
    )
    if regenerate is not None:
        regenerate(session)
```

- 呼び出し元は次の3か所。
  - ログイン（`views.py:135`）
  - ログアウト（`views.py:154`）
  - 「ログインしたままにする」のCookieでの復元（`_renew_session_on_remember_login()`、`views.py:66`）

### `.venv/.../flask_session/base.py:261-270`

```python
def regenerate(self, session: ServerSideSession) -> None:
    """Regenerate the session id for the given session.
    ..."""
    if session:
        # Remove the old session
        # from storage
        self._delete_session(
            self._get_store_id(session.sid)
        )
        # Generate a new session ID
        new_sid = self._generate_sid(self.sid_length)
        session.sid = new_sid
        # Mark the session as modified
        # to ensure it gets saved
        session.modified = True
```

- `if session:`で空のセッションを無視するので、`session.clear()`の直後に呼ぶと何も起きない。\
  `_regenerate_session_id()`のdocstringの「値を書いたあとに呼ぶこと」はこのため。
- 古いキーを`DEL`するので、ログアウトすると盗まれたCookie（古いID）も使えなくなる。\
  `tests/test_session.py`のCookie盗用のテストがこれを確認している。

### ログイン成功時の流れ（`src/fl_demonstro/accounts/views.py:132-135`）

各行のコードと、Redisへの影響。

1. `session.clear()`：まだ何もしない（メモリ上のdictを空にするだけ）。
2. `login_user(...)` / `flash(...)`：まだ何もしない（`_user_id`や`_flashes`をdictに入れるだけ）。
3. `_regenerate_session_id()`：`DEL session:<古い ID>`。\
   新しいIDを発行する。
4. リクエストの終わり（`save_session()`）：`SET session:<新しい ID> <中身> EX 43200`。\
   Cookieも新しいIDになる。

### キーの作り方

#### `.venv/.../limits/limits.py:115-124`

`key_for()`が、識別子・スコープ・制限の内容を`/`でつなぐ。

`RedisStorage`がさらに`LIMITS:`を付ける。

```python
remainder = "/".join(
    [safe_string(k) for k in identifiers]
    + [
        safe_string(self.amount),
        safe_string(self.multiples),
        self.GRANULARITY.name,
    ]
)

return f"{self.namespace}/{remainder}"
```

- `identifiers`は`[key_func() の結果, スコープ（エンドポイント名）]`。
- `"5 per minute;20 per hour"`は2つの制限として別々に数えるので、キーも2つになる。

ログインの3つの制限のキー：

- IPごと・1分5回：`LIMITS:LIMITER/127.0.0.1/accounts.login/5/1/minute`
- IPごと・1時間20回：`LIMITS:LIMITER/127.0.0.1/accounts.login/20/1/hour`
- ユーザー名ごと・1時間10回：`LIMITS:LIMITER/login:taro/accounts.login/10/1/hour`

### 数え方（固定ウィンドウ）

`RATELIMIT_STRATEGY`を指定していないので、既定の`fixed-window`が使われる。

#### `.venv/.../limits/strategies.py:144-177`（docstring省略）

```python
def hit(
    self,
    item: RateLimitItem,
    *identifiers: str,
    cost: int = 1,
) -> bool:
    return (
        self.storage.incr(
            item.key_for(*identifiers),
            item.get_expiry(),
            amount=cost,
        )
        <= item.amount
    )


def test(
    self,
    item: RateLimitItem,
    *identifiers: str,
    cost: int = 1,
) -> bool:
    return (
        self.storage.get(item.key_for(*identifiers))
        < item.amount - cost + 1
    )
```

- `hit()`は回数を増やしてから上限と比べる。\
  `test()`は今の回数を`GET`で読んで比べるだけで、書き込まない。

#### `.venv/.../limits/resources/redis/lua_scripts/incr_expire.lua`

`RedisStorage.incr()`がRedis上で実行するスクリプト。

```lua
local current
local amount = tonumber(ARGV[2])
current = redis.call("incrby", KEYS[1], amount)

if tonumber(current) == amount then
    redis.call("expire", KEYS[1], ARGV[1])
end

return current
```

- `INCRBY`と`EXPIRE`をLuaで1つにまとめているので、2つのワーカーが同時に数えても取りこぼさない（アトミック）。
- `EXPIRE`は最初の1回（値が`amount`になったとき）だけ。\
  2回目以降はTTLを延ばさないので、最初の失敗から60秒（3600秒）たつとキーが消えて回数が0に戻る。

## 6. 実際に書き込まれるキー（確認結果）

使い捨てのRedisコンテナを立て、テストクライアントでCSRFと回数制限を有効にして操作し、各操作のあとのキーを一覧した。

セッションIDは省略し、値はmsgpackを戻して表示している。

### `GET /accounts/login`

- `session:FCA1…`（TTL 43200）

```python
{"_permanent": True, "csrf_token": "3ccf…"}
```

### ログイン失敗（1回目）

次の3つのキーができ、値はどれも`1`。

- `LIMITS:LIMITER/127.0.0.1/accounts.login/5/1/minute`（TTL 60）
- `LIMITS:LIMITER/127.0.0.1/accounts.login/20/1/hour`（TTL 3600）
- `LIMITS:LIMITER/login:taro/accounts.login/10/1/hour`（TTL 3600）

### ログイン失敗（2回目）

- 上の3つのキーの値が`2`になる。

### ログイン成功

- 上の3つのキーの値は`2`のまま。
- `session:FCA1…`は消える（`DEL`）。
- `session:u4_0…`（TTL 43200）ができる。

```python
{
    "_permanent": True,
    "_user_id": "1",
    "_fresh": True,
    "_id": "…",
    "_flashes": [["success", "ログインしました。"]],
}
```

### `GET /`（ログイン中）

- `session:u4_0…`（TTL 43200）から`_flashes`が消え、新しい`csrf_token`が入る。

### 分かること

- 入力した`Taro`も`login:taro`として数えられる（`_login_username_key()`で小文字にしているため）。
- ログイン成功でIDが変わり、ログイン前の`csrf_token`も捨てられている（`session.clear()`のため）。

## 7. Redisコンテナの設定

### `compose.yaml:49-66`

```yaml
redis:
  # 公式イメージ（alpine は小さい版）。
  # 起動時に redis ユーザーに切り替えてから動く。
  image: redis:8-alpine
  # --appendonly yes: データをファイルにも書き出し、
  # Redis を再起動してもログイン状態が消えないようにする
  # --maxmemory: 使うメモリの上限。いっぱいになったら、
  # しばらく使われていないものから消す
  #   （ログイン画面を開くたびにセッションが1つ作られるので、
  #   上限がないと増え続けてしまう）
  command:
    - redis-server
    - --appendonly
    - "yes"
    - --maxmemory
    - 128mb
    - --maxmemory-policy
    - allkeys-lru
  volumes:
    # AOF（書き出したデータ）を置く場所
    - redis-data:/data
  restart: unless-stopped
```

- `--appendonly yes`：書き込みをAOFファイル（ボリューム`redis-data`）にも残すので、Redisを再起動してもセッションと回数が残る。
- `allkeys-lru`：上限に達すると、TTLの有無に関係なく最近使われていないキーから消す。\
  セッションも回数制限のカウンターも対象なので、メモリが足りなくなると「ログアウトされる」「回数が0に戻る」ことがある。

## 8. Redisが止まっているとき

接続できないポートを`REDIS_URL`に指定して確認した結果。

- `create_app()`：成功。`Redis.from_url()`は接続しない。
- 未ログインで`GET /`：200。セッションが空なのでRedisに触れない。
- `GET /accounts/login`：500。CSRFトークンをセッションに`SET`しようとして失敗する。
- `POST /accounts/login`：500。回数制限の`GET` / `INCRBY`が失敗する。

回数制限は`RATELIMIT_SWALLOW_ERRORS`（エラーを無視して通す）も`RATELIMIT_IN_MEMORY_FALLBACK_ENABLED`（メモリに切り替える）も設定していないので、Redisのエラーがそのまま500になる。

制限をかけずに通してしまうよりは安全側の動き。
