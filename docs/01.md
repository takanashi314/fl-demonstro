# Redis への書き込みの解説（01）

## 全体像

アプリのコードは Redis を直接操作していない（`set` や `incr` を自分で呼んでいない）。Redis に書き込むのは次の2つの拡張機能で、アプリ側がやっているのは「どの Redis を使うか」の設定だけ。

| 用途 | 書き込むライブラリ | キー | 値 | TTL |
| --- | --- | --- | --- | --- |
| セッション | Flask-Session | `session:<セッション ID>` | セッションの dict（msgpack） | `PERMANENT_SESSION_LIFETIME`（12時間） |
| 回数制限 | Flask-Limiter（中身は `limits`） | `LIMITS:LIMITER/<識別子>/<エンドポイント>/<回数>/<1>/<単位>` | 回数（整数） | 制限の期間（60秒・3600秒） |

どちらも同じ Redis の DB 0 を使い、キーの接頭辞（`session:` / `LIMITS:`）で分かれている。Redis クライアントは別々で、セッションはアプリが作った `Redis` オブジェクト、回数制限は `limits` が URI から自分で作る接続を使う。

Redis を使う理由は、本番（Docker）の gunicorn が `--workers 2` で動くため。回数制限を `memory://` にすると記録がワーカー（プロセス）ごとに別になり、制限が実質2倍に緩む。

## 2. セッションの保存先を選ぶ

### `src/fl_demonstro/__init__.py:34-45`

```python
def _configure_session_storage(app: Flask) -> None:
    """セッションの保存先を決める（設定で指定されていればそれを使う）。"""
    if app.config.get("SESSION_TYPE"):
        return
    if redis_url := app.config.get("REDIS_URL"):
        app.config["SESSION_TYPE"] = "redis"
        app.config["SESSION_REDIS"] = Redis.from_url(redis_url)
    else:
        app.config["SESSION_TYPE"] = "cachelib"
        app.config["SESSION_CACHELIB"] = FileSystemCache(
            str(Path(app.instance_path) / "sessions"), threshold=1000
        )
```

- `SESSION_TYPE = "redis"` と `SESSION_REDIS`（Redis クライアント）を config に入れておくと、Flask-Session がそれを読んで `RedisSessionInterface` を `app.session_interface` に設定する。
- `Redis.from_url()` はクライアント（コネクションプール）を作るだけで、この時点では接続しない。最初のコマンドで初めて接続するので、Redis が止まっていても `create_app()` は成功する。
- `tests/test_session.py` の `test_session_storage_is_chosen_from_redis_url` は、この選び分けを確認している（接続しないので Redis がなくても通る）。

### `src/fl_demonstro/__init__.py:100-103`

```python

    login_manager.init_app(app)
    _configure_session_storage(app)
    server_session.init_app(app)
```

- `server_session.init_app(app)` は、呼ばれた時点の `SESSION_TYPE` / `SESSION_REDIS` を読む。そのため `_configure_session_storage()` はその前に呼ぶ必要がある。

## 3. Flask-Session が Redis に書き込む処理（ライブラリ側）

実際に `SET` / `GET` / `DEL` を呼んでいるのは `RedisSessionInterface`。いつ呼ぶかは、共通の基底クラス `ServerSideSessionInterface` が決めている。

### `.venv/.../flask_session/redis/redis.py:62-85`

```python
    def _retrieve_session_data(self, store_id: str) -> Optional[dict]:
        # Get the saved session (value) from the database
        serialized_session_data = self.client.get(store_id)
        if serialized_session_data:
            return self.serializer.decode(serialized_session_data)
        return None

    def _delete_session(self, store_id: str) -> None:
        self.client.delete(store_id)

    def _upsert_session(
        self, session_lifetime: TimeDelta, session: ServerSideSession, store_id: str
    ) -> None:
        storage_time_to_live = total_seconds(session_lifetime)

        # Serialize the session data
        serialized_session_data = self.serializer.encode(session)

        # Update existing or create new session in the database
        self.client.set(
            name=store_id,
            value=serialized_session_data,
            ex=storage_time_to_live,
        )
```

- キー（`store_id`）は `key_prefix + sid`、つまり `session:` + セッション ID。セッション ID は `secrets.token_urlsafe(32)`（43文字）。
- 値は msgspec の msgpack でシリアライズした dict。
- `SET ... EX 43200` なので、Redis 側の TTL で古いセッションが自動で消える（ファイル保存のような掃除が要らない）。
- ブラウザの Cookie に入るのはセッション ID だけで、中身はサーバー側にしかない。

### `.venv/.../flask_session/base.py:274-305`（抜粋）

リクエストの最後に Flask が呼ぶ `save_session()`。

```python
    def save_session(self, app, session, response) -> None:
        ...
        store_id = self._get_store_id(session.sid)
        ...
        # If the session is empty, do not save it to the database or set a cookie
        if not session:
            # If the session was deleted (empty and modified), delete the saved session ...
            if session.modified:
                self._delete_session(store_id)
                response.delete_cookie(key=name, domain=domain, path=path)
                response.vary.add("Cookie")
            return

        if not self.should_set_storage(app, session):
            return

        # Update existing or create new session in the database
        self._upsert_session(app.permanent_session_lifetime, session, store_id)
```

- セッションが空なら Redis に書かない。未ログインでトップページを見るだけでは、キーは作られない。
- ログイン画面を開くと CSRF トークンがセッションに入るので、ログインしていなくてもキーが1つ作られる。compose.yaml で `maxmemory` を付けている理由がこれ（7章）。

### `.venv/.../flask_session/base.py:221-232`（docstring 省略）

```python
    def should_set_storage(self, app: Flask, session: ServerSideSession) -> bool:
        return session.modified or app.config["SESSION_REFRESH_EACH_REQUEST"]
```

- Flask の `SESSION_REFRESH_EACH_REQUEST` は既定で `True`。そのため、中身のあるセッションはリクエストのたびに `SET` され直し、TTL が12時間に戻る。config のコメント「操作がなければ12時間で期限切れ」はこの動きのこと。

## 4. アプリ側でセッション ID を作り直す

アプリのコードで Redis の中身に影響するのは、セッション ID の作り直しだけ。

### `src/fl_demonstro/accounts/views.py:38-47`

```python
def _regenerate_session_id() -> None:
    """セッション ID を新しくし、古い ID のセッションをサーバーから消す。

    Flask-Session の regenerate() は中身が空のセッションでは何もしないので、
    セッションに値を書いたあと（login_user() や flash() のあと）に呼ぶこと。
    """
    regenerate = getattr(current_app.session_interface, "regenerate", None)
    if regenerate is not None:
        regenerate(session)
```

- 呼び出し元は、ログイン（`views.py:135`）、ログアウト（`views.py:154`）、「ログインしたままにする」の Cookie での復元（`_renew_session_on_remember_login()`、`views.py:66`）の3か所。

### `.venv/.../flask_session/base.py:261-270`

```python
    def regenerate(self, session: ServerSideSession) -> None:
        """Regenerate the session id for the given session. ..."""
        if session:
            # Remove the old session from storage
            self._delete_session(self._get_store_id(session.sid))
            # Generate a new session ID
            new_sid = self._generate_sid(self.sid_length)
            session.sid = new_sid
            # Mark the session as modified to ensure it gets saved
            session.modified = True
```

- `if session:` で空のセッションを無視するので、`session.clear()` の直後に呼ぶと何も起きない。`_regenerate_session_id()` の docstring の「値を書いたあとに呼ぶこと」はこのため。
- 古いキーを `DEL` するので、ログアウトすると盗まれた Cookie（古い ID）も使えなくなる。`tests/test_session.py` の Cookie 盗用のテストがこれを確認している。

### ログイン成功時の流れ（`src/fl_demonstro/accounts/views.py:132-135`）

| コード | Redis への影響 |
| --- | --- |
| `session.clear()` | まだ何もしない（メモリ上の dict を空にするだけ） |
| `login_user(...)` / `flash(...)` | まだ何もしない（`_user_id` や `_flashes` を dict に入れるだけ） |
| `_regenerate_session_id()` | `DEL session:<古い ID>`。新しい ID を発行 |
| リクエストの終わり（`save_session()`） | `SET session:<新しい ID> <中身> EX 43200`。Cookie も新しい ID に |

### キーの作り方

#### `.venv/.../limits/limits.py:115-124`

`key_for()` が、識別子・スコープ・制限の内容を `/` でつなぐ。`RedisStorage` がさらに `LIMITS:` を付ける。

```python
        remainder = "/".join(
            [safe_string(k) for k in identifiers]
            + [
                safe_string(self.amount),
                safe_string(self.multiples),
                self.GRANULARITY.name,
            ]
        )

        return f"{self.namespace}/{remainder}"
```

- `identifiers` は `[key_func() の結果, スコープ（エンドポイント名）]`。
- `"5 per minute;20 per hour"` は2つの制限として別々に数えるので、キーも2つになる。

| 制限 | キー |
| --- | --- |
| IP ごと・1分5回 | `LIMITS:LIMITER/127.0.0.1/accounts.login/5/1/minute` |
| IP ごと・1時間20回 | `LIMITS:LIMITER/127.0.0.1/accounts.login/20/1/hour` |
| ユーザー名ごと・1時間10回 | `LIMITS:LIMITER/login:taro/accounts.login/10/1/hour` |

### 数え方（固定ウィンドウ）

`RATELIMIT_STRATEGY` を指定していないので、既定の `fixed-window` が使われる。

#### `.venv/.../limits/strategies.py:144-177`（docstring 省略）

```python
    def hit(self, item: RateLimitItem, *identifiers: str, cost: int = 1) -> bool:
        return (
            self.storage.incr(
                item.key_for(*identifiers),
                item.get_expiry(),
                amount=cost,
            )
            <= item.amount
        )

    def test(self, item: RateLimitItem, *identifiers: str, cost: int = 1) -> bool:
        return self.storage.get(item.key_for(*identifiers)) < item.amount - cost + 1
```

- `hit()` は回数を増やしてから上限と比べる。`test()` は今の回数を `GET` で読んで比べるだけで、書き込まない。

#### `.venv/.../limits/resources/redis/lua_scripts/incr_expire.lua`

`RedisStorage.incr()` が Redis 上で実行するスクリプト。

```lua
local current
local amount = tonumber(ARGV[2])
current = redis.call("incrby", KEYS[1], amount)

if tonumber(current) == amount then
    redis.call("expire", KEYS[1], ARGV[1])
end

return current
```

- `INCRBY` と `EXPIRE` を Lua で1つにまとめているので、2つのワーカーが同時に数えても取りこぼさない（アトミック）。
- `EXPIRE` は最初の1回（値が `amount` になったとき）だけ。2回目以降は TTL を延ばさないので、最初の失敗から60秒（3600秒）たつとキーが消えて回数が0に戻る。

### `deduct_when` による「失敗だけ数える」

#### `.venv/.../flask_limiter/_extension.py:1071-1075`（ビューの前）

## 6. 実際に書き込まれるキー（確認結果）

使い捨ての Redis コンテナを立て、テストクライアントで CSRF と回数制限を有効にして操作し、各操作のあとのキーを一覧した（セッション ID は省略、値は msgpack を戻して表示）。

| 操作 | キー | TTL | 値 |
| --- | --- | --- | --- |
| `GET /accounts/login` | `session:FCA1…` | 43200 | `{'_permanent': True, 'csrf_token': '3ccf…'}` |
| ログイン失敗（1回目） | `LIMITS:LIMITER/127.0.0.1/accounts.login/5/1/minute` | 60 | `1` |
| | `LIMITS:LIMITER/127.0.0.1/accounts.login/20/1/hour` | 3600 | `1` |
| | `LIMITS:LIMITER/login:taro/accounts.login/10/1/hour` | 3600 | `1` |
| ログイン失敗（2回目） | 上の3つ | 同上 | `2` |
| ログイン成功 | 上の3つ | 同上 | `2` のまま |
| | `session:FCA1…` | — | 消える（`DEL`） |
| | `session:u4_0…` | 43200 | `{'_permanent': True, '_user_id': '1', '_fresh': True, '_id': '…', '_flashes': [['success', 'ログインしました。']]}` |
| `GET /`（ログイン中） | `session:u4_0…` | 43200 | `_flashes` が消え、新しい `csrf_token` が入る |

- 入力した `Taro` も `login:taro` として数えられる（`_login_username_key()` で小文字にしているため）。
- ログイン成功で ID が変わり、ログイン前の `csrf_token` も捨てられている（`session.clear()` のため）。

## 7. Redis コンテナの設定

### `compose.yaml:27-42`

```yaml
  redis:
    image: redis:8-alpine
    # --appendonly yes: データをファイルにも書き出し、Redis を再起動してもログイン状態が消えないようにする
    # --maxmemory: 使うメモリの上限。いっぱいになったら、しばらく使われていないものから消す
    #   （ログイン画面を開くたびにセッションが1つ作られるので、上限がないと増え続けてしまう）
    command:
      - redis-server
      - --appendonly
      - "yes"
      - --maxmemory
      - 128mb
      - --maxmemory-policy
      - allkeys-lru
    volumes:
      - redis-data:/data
    restart: unless-stopped
```

- `--appendonly yes`：書き込みを AOF ファイル（ボリューム `redis-data`）にも残すので、Redis を再起動してもセッションと回数が残る。
- `allkeys-lru`：上限に達すると、TTL の有無に関係なく最近使われていないキーから消す。セッションも回数制限のカウンターも対象なので、メモリが足りなくなると「ログアウトされる」「回数が0に戻る」ことがある。

## 8. Redis が止まっているとき

接続できないポートを `REDIS_URL` に指定して確認した結果。

| 場面 | 結果 | 理由 |
| --- | --- | --- |
| `create_app()` | 成功 | `Redis.from_url()` は接続しない |
| 未ログインで `GET /` | 200 | セッションが空なので Redis に触れない |
| `GET /accounts/login` | 500 | CSRF トークンをセッションに `SET` しようとして失敗 |
| `POST /accounts/login` | 500 | 回数制限の `GET` / `INCRBY` が失敗 |

回数制限は `RATELIMIT_SWALLOW_ERRORS`（エラーを無視して通す）も `RATELIMIT_IN_MEMORY_FALLBACK_ENABLED`（メモリに切り替える）も設定していないので、Redis のエラーがそのまま 500 になる。制限をかけずに通してしまうよりは安全側の動き。
