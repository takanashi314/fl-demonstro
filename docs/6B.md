# docker compose up --buildの流れB：イメージを用意する（6B）

`docs/06.md`のB（7〜31）を詳しくしたもの。

コードブロックの1行目に、抜き出したファイルと行番号を書いている。

コードやログは、iPhoneの縦画面で読めるよう、改行やインデントを変えたり、一部を省いたりしている。

出力は、2026-11-27に手元で実行して取ったもの（Docker 29.7.2、Compose v5.5.0、BuildKit v0.32.2）。

各命令のフラグの意味は`Dockerfile`のコメントに書いてあるので、ここでは繰り返さず、ビルドの中で何が起きるかを追う。

## 全体像

Bの段階は、次の順に進む。

- Composeが、ビルドをBuildKitに頼む（1章）
- BuildKitが、Dockerfileを処理のグラフにする（2章）
- ビルドコンテキストを受け取る（3章）
- グラフを、キャッシュを確かめながら並列に実行する（4〜5章）
- 1段目で、uvがパッケージを入れる（6〜7章）
- 2段目を組み立てて、イメージとして書き出す（8〜9章）

ログの`#1`・`#2`…は、BuildKitの処理の単位（vertex）の番号。\
処理は並列に進むので、同じ番号が間をあけて何度も出たり、Dockerfileと違う順で出たりする。

ここに載せた形のログは、`docker compose --progress=plain up --build`で見られる。

## 1. Composeがビルドを頼む

1. `redis`は`image:`だけなので、ビルドしない。\
   手元に`redis:8-alpine`がなければ、先にpullする（`pull_policy`の既定は`missing`）。\
   手元にあれば、Docker Hubに新しい版があってもそのまま使う。
2. `web`は`build: .`で`image:`がないので、イメージの名前は「プロジェクト名-サービス名」の`fl-demonstro-web`（タグは`latest`）になる。
3. Compose v5は、ビルドを自分では行わず、buildxの`bake`に任せる。\
   ビルドの設定（コンテキスト・Dockerfile・イメージの名前・ラベル）を、標準入力でbakeに渡す。

```text
#1 [internal] load local bake definitions
#1 reading from stdin 544B done
```

4. Composeは、イメージにラベルを3つ付ける。\
   後でComposeが、どのプロジェクトのイメージかを見分けるのに使う。

```text
$ docker image inspect fl-demonstro-web \
    --format '{{json .Config.Labels}}'
{"com.docker.compose.project":"fl-demonstro",
 "com.docker.compose.service":"web",
 "com.docker.compose.version":"5.5.0"}
```

（出力は折り返している）

## 2. Dockerfileを読む

5. Dockerfileを受け取る（#2）。\
   `Dockerfile`は`.dockerignore`でビルドコンテキストから外しているが、それとは別に送られる。

```text
#2 [internal] load build definition from Dockerfile
#2 transferring dockerfile: 13.06kB done
```

6. 1行目の`# syntax=docker/dockerfile:1`を見て、フロントエンドのイメージのタグ`1`が、今どのダイジェストを指すかをDocker Hubに問い合わせる（#3）。\
   問い合わせに使うトークンを、#4で取ってくる。\
   キャッシュが全部効くビルドでも毎回問い合わせる（今回は0.7〜1.3秒かかった）。

```text
#3 resolve image config for
   docker-image://docker.io/docker/dockerfile:1
#4 [auth] docker/dockerfile:pull token for
   registry-1.docker.io
#3 DONE 1.3s
#5 docker-image://docker.io/docker/dockerfile:1
   @sha256:572cebbc2b15...
#5 CACHED
```

7. そのダイジェストのイメージは手元にあるので、取ってこない（`CACHED`）。\
   フロントエンドは、Dockerfileを解析して、BuildKitが実行する処理のグラフ（LLB）に変える。\
   コメントはここで消えるので、コメントだけを変えてもキャッシュは外れない。
8. `FROM`と`COPY --from`で使うイメージの設定を読む（#6・#7）。\
   どちらも手元にあるので、レジストリには問い合わせない（`[auth]`の行が出ず、`0.0s`で終わる）。\
   そのため、`3.15-slim`のタグが新しいパッチ版に付け替えられても、手元にある間は古いほうを使い続ける。\
   取り直すときは`docker compose build --pull`を使う。

```text
#6 [internal] load metadata for
   ghcr.io/astral-sh/uv:0.13.5
#6 DONE 0.0s
#7 [internal] load metadata for
   docker.io/library/python:3.15-slim
#7 DONE 0.0s
```

## 3. ビルドコンテキストを受け取る

9. `.dockerignore`を受け取る（#8）。\
   BuildKitは、この中身を使って、ビルドコンテキストから送らせないファイルを決める。
10. ビルドコンテキストを受け取る（#11）。\
    送るのはDockerのクライアント（buildx）で、BuildKitは前回受け取った内容を覚えていて、変わったファイルだけを送らせる。

```text
#11 [internal] load build context
#11 transferring context: 34.73kB done
```

（その後のビルドでは`2.60kB`だった）

11. 送られたのは48ファイル（`COPY . /ctx`するだけのDockerfileで、中身を一覧にして確かめた）。
    - `src/`（25）・`migrations/`（7）・`docs/`（7）
    - `pyproject.toml`・`uv.lock`・`README.md`・`docker/entrypoint.sh`
    - `.env.example`・`.python-version`・`.pre-commit-config.yaml`・`.coverage`・`.github/`の中身
12. 送られなかったもの：`.env`・`.git`・`.venv`・`tests/`・`instance/`・`.docs/`・`.claude`・`.dev_cache/`・`__pycache__`と`.pyc`・`Dockerfile`・`compose.yaml`・`.dockerignore`。
13. `.dockerignore`のパターンは、ビルドコンテキストの直下からの相対パスとして照合する（`.gitignore`のように、どの深さにも当てはまるわけではない）。\
    `instance/`は直下の`instance`だけを外し、`src/instance`があっても外さない。\
    どの深さにも当てはめたいものは、`**/__pycache__`のように`**/`を付けて書いている。
14. 送られることと、イメージに入ることは別。\
    `docs/`や`.coverage`は送られるが、`COPY`していないのでイメージには入らず、変えてもキャッシュは外れない（`COPY`のキャッシュは、コピーするファイルの中身だけで決まる。5章）。

## 4. 処理のグラフと並列の実行

15. ログの`[builder 3/8]`・`[stage-1 2/7]`は、どの段の何番目の処理かを表す。\
    名前を付けた1段目は`builder`、名前のない2段目は番号で`stage-1`（0から数えて1番目）と表示される。
16. 数えるのは、ファイルシステムを作る・変える命令（`FROM`・`COPY`・`RUN`・`WORKDIR`）だけ。\
    `ENV`・`USER`・`EXPOSE`・`ENTRYPOINT`・`CMD`はイメージの設定を変えるだけなので、処理として数えない（8章）。

```text
builder 1/8  FROM python:3.15-slim
builder 2/8  COPY --from=ghcr.io/astral-sh/uv:0.13.5 ...
builder 3/8  WORKDIR /app
builder 4/8  COPY pyproject.toml uv.lock ./
builder 5/8  RUN uv sync ... --no-install-project
builder 6/8  COPY README.md ./
builder 7/8  COPY src ./src
builder 8/8  RUN uv sync ... --no-editable
stage-1 1/7  FROM python:3.15-slim
stage-1 2/7  RUN groupadd ... && useradd ...
stage-1 3/7  WORKDIR /app
stage-1 4/7  COPY --from=builder /app/.venv /app/.venv
stage-1 5/7  COPY migrations ./migrations
stage-1 6/7  COPY docker/entrypoint.sh ...
stage-1 7/7  RUN mkdir -p /app/instance && chown ...
```

17. BuildKitは、処理を依存関係のグラフとして扱い、互いに依存しない処理を同時に進める。\
    2段目の1/7〜3/7は1段目に依存しないので、1段目のuv syncと同時に進む。\
    1段目の結果を使う4/7（`COPY --from=builder`）だけが、1段目の8/8を待つ。

キャッシュを使わずにビルドしたときのログ（`docker buildx build --no-cache`）：

```text
#10 [stage-1 2/7] RUN groupadd ...
#10 ...
#11 [builder 2/8] COPY --from=ghcr.io/astral-sh/uv ...
#11 DONE 0.5s
#12 [builder 3/8] WORKDIR /app
#12 DONE 0.1s
#13 [builder 4/8] COPY pyproject.toml uv.lock ./
#13 DONE 0.1s
#14 [builder 5/8] RUN ... --no-install-project
#14 ...
#10 [stage-1 2/7] RUN groupadd ...
#10 DONE 1.2s
#15 [stage-1 3/7] WORKDIR /app
#15 DONE 0.1s
#14 [builder 5/8] RUN ... --no-install-project
#14 DONE 6.5s
（中略）
#19 [stage-1 4/7] COPY --from=builder /app/.venv ...
#19 DONE 1.8s
```

（`#10 ...`は「まだ終わっていない」の印。#14の途中で、#10と#15が終わっている）

18. キャッシュが全部効いたビルドでは、すべてが`CACHED`になる。\
    キャッシュの確認も並列に進むので、表示の順はDockerfileの順と関係なくなる。

```text
#12 [builder 7/8] COPY src ./src
#12 CACHED
#13 [builder 3/8] WORKDIR /app
#13 CACHED
#14 [builder 6/8] COPY README.md ./
#14 CACHED
#15 [stage-1 6/7] COPY docker/entrypoint.sh ...
#15 CACHED
```

19. BuildKitは、最後の段（2段目）から逆にたどって、必要な処理だけを実行する。\
    1段目は4/7から参照されているので実行される。どこからも参照されない段があれば、実行されない。

## 5. キャッシュの判定

20. 各処理のキャッシュのキーは、「1つ前の処理のキー」と「その処理の中身」から作られる。\
    1つ前のキーを含むので、ある処理でキャッシュが外れると、同じ段のそれより後の処理もすべて外れる。
21. 「中身」に入るものは、処理の種類ごとに違う。
    - `FROM`：イメージのダイジェスト。
    - `RUN`：コマンドの文字列と、そのときの環境変数・作業フォルダ・ユーザー・`--mount`の指定。コマンドの外の状態（PyPIに新しい版が出たなど）は見ない。
    - `COPY`：コピー元のファイルの中身と属性から計算したチェックサム。更新日時は含まない。
    - `COPY --from=builder`：1段目の`/app/.venv`の中身のチェックサム。
22. `RUN --mount=type=cache`のフォルダの中身は、キーに入らない。\
    キャッシュのフォルダに何が入っていても、`RUN`のキャッシュが効くかどうかは変わらない。
23. 1段目の`ENV`（`UV_COMPILE_BYTECODE`など）は、後の`RUN`のキーに入る（環境変数として`RUN`に渡るため）。\
    値を変えると、builder 5/8以降を実行し直す。
24. ファイルを変えたとき、どこから実行し直すか。
    - `src/`の中：builder 7/8から。8/8で作り直した`.venv`の中身が変わるので、stage-1 4/7以降も実行し直す。builder 5/8（依存パッケージ）と、stage-1 2/7・3/7はキャッシュが効く。
    - `pyproject.toml`・`uv.lock`：builder 4/8から。依存パッケージを入れ直す。
    - `README.md`：builder 6/8から。
    - `migrations/`：stage-1 5/7から。1段目はすべてキャッシュが効く。
    - `docker/entrypoint.sh`：stage-1 6/7から。
    - `Dockerfile`のコメント：どこも実行し直さない（7）。
    - `Dockerfile`の2段目の`ENV`より後：処理ではないので、どこも実行し直さず、イメージの設定だけが変わる。
25. キャッシュが全部効くと、出来上がるイメージのIDも前と同じになる（今回は、ビルドの前も後も`1a2bde453ed7`）。\
    そのため、コードを変えずに`up --build`を繰り返しても、webのコンテナは作り直されない（`docs/6D.md`の1章）。

## 6. 1段目：依存パッケージを入れる

builder 5/8の`uv sync --locked --no-dev --no-install-project`のログ：

```text
#14 0.813 Using CPython 3.15.2 interpreter at:
          /usr/local/bin/python3
#14 0.813 Creating virtual environment at: .venv
#14 0.818 Resolved 63 packages in 1ms
#14 1.011 Downloading sqlalchemy (4.4MiB)
#14 1.179  Downloaded sqlalchemy
#14 1.180 Prepared 32 packages in 361ms
#14 1.354 Installed 32 packages in 173ms
#14 2.372 Bytecode compiled 911 files in 1.01s
#14 2.372  + alembic==1.20.1
#14 2.372  + argon2-cffi==25.1.0
（中略）
#14 2.372  + wtforms==3.3.2
```

（`--no-cache`のビルドのログ。2列目は、その処理を始めてからの秒数）

26. Pythonを探す。\
    `UV_PYTHON_DOWNLOADS=never`なので、候補はイメージの`/usr/local/bin/python3`（3.15.2）だけで、`requires-python = "==3.15.*"`に合うのでそれを使う。
27. `/app/.venv`に仮想環境を作る。\
    `bin/python`は`/usr/local/bin/python3`へのシンボリックリンクで、`pyvenv.cfg`にもその場所が書かれる。

```text
$ cat /app/.venv/pyvenv.cfg
home = /usr/local/bin
implementation = CPython
uv = 0.13.5
version_info = 3.15.2
include-system-site-packages = false
prompt = fl-demonstro
```

28. `Resolved 63 packages`：`--locked`なので、`uv.lock`が`pyproject.toml`と合っているかを確かめる。\
    63は`uv.lock`の全パッケージ（devグループとプロジェクト自身を含む）の数。合っていなければ、ここで失敗して止まる。
29. 実際に入れるのは、そのうちの32（mainの依存関係だけ）。\
    `--no-dev`でdevグループを、`--no-install-project`でプロジェクト自身を除いている。
30. `Prepared`：キャッシュ（`/root/.cache/uv`）にないものを取ってきて、展開してキャッシュに置く。\
    今回取ってきたのは`sqlalchemy`だけで、残りはキャッシュにあった。
31. `Installed`：キャッシュから`.venv`のsite-packagesに入れる。\
    `UV_LINK_MODE=copy`なので、ファイルをコピーする。
32. `Bytecode compiled 911 files`：site-packagesの`.py`を`.pyc`にする（`UV_COMPILE_BYTECODE=1`）。
33. 最後に、入れたパッケージを`+ 名前==版`で並べる。devグループのもの（pytestなど）は並ばない。

## 7. 1段目：アプリを入れる

builder 8/8の`uv sync --locked --no-dev --no-editable`のログ：

```text
#18 0.461 Resolved 63 packages in 1ms
#18 0.465    Building fl-demonstro @ file:///app
#18 0.476       Built fl-demonstro @ file:///app
#18 0.484 Prepared 1 package in 20ms
#18 0.495 Installed 1 package in 10ms
#18 0.609 Bytecode compiled 924 files in 113ms
#18 0.609  + fl-demonstro==0.1.0 (from file:///app)
```

34. 依存パッケージの32は5/8で入っているので、入れ直さない。\
    `uv sync`は、入っているものと`uv.lock`を比べて、足りないものだけを入れる。
35. `Building`〜`Built`：`pyproject.toml`の`build-backend = "uv_build"`で、`/app`からwheelを作る（11ミリ秒）。\
    wheelの`WHEEL`ファイルは次のとおりで、どのPythonでも使える純Pythonのパッケージ（`py3-none-any`）になる。

```text
Wheel-Version: 1.0
Generator: uv 0.13.5
Root-Is-Purelib: true
Tag: py3-none-any
```

36. wheelには、`src/fl_demonstro/`の中のすべてのファイルが入る（`.py`のほか、`templates/`のHTMLや`accounts/data/`のファイルも）。\
    インストールした結果の`RECORD`（入れたファイルの一覧）には、`src/`から送られた25ファイルがそのまま並ぶ。
37. `--no-editable`なので、site-packagesに`fl_demonstro/`がコピーされる。\
    editableなら`.pth`ファイルで`src/`を`sys.path`に足すが、このイメージのsite-packagesに`.pth`ファイルは1つもない。\
    editableでないことは、`direct_url.json`にも記録される。

```text
$ cat .../fl_demonstro-0.1.0.dist-info/direct_url.json
{"url":"file:///app","dir_info":{"editable":false}}
```

38. `Bytecode compiled 924 files`：911から増えた13が、`fl_demonstro`の`.py`の数。\
    924はsite-packages全体を数えた数で、5/8で作った`.pyc`は作り直さないので、113ミリ秒で終わる。
39. この時点で、1段目の`/app`には`pyproject.toml`・`uv.lock`・`README.md`・`src/`・`.venv/`がある。\
    2段目に持っていくのは`.venv/`だけ。

## 8. 2段目を組み立てる

40. もう一度`python:3.15-slim`から始める（stage-1 1/7）。\
    1段目と同じイメージなので、取ってくることも展開することもない。
41. `groupadd`・`useradd`（stage-1 2/7）：`/etc/passwd`・`/etc/group`・`/etc/shadow`・`/etc/gshadow`に1行ずつ足し、`/home/app`を作って`/etc/skel`の中身（`.bashrc`・`.profile`・`.bash_logout`）をコピーする。\
    レイヤーは8.85kB。
42. `WORKDIR /app`（stage-1 3/7）：`/app`を作るだけの、中身のないレイヤーになる。
43. `COPY --from=builder`（stage-1 4/7）：52MBのレイヤー。\
    ファイルの更新日時も、1段目で作ったときのままコピーされる。\
    キャッシュが効いたビルドでは前のレイヤーをそのまま使うので、日付も前のビルドのまま変わらない。
44. コピー先は、1段目と同じ`/app/.venv`でなければならない。\
    仮想環境の中に、場所を絶対パスで書いたものがあるため。
    - `bin/flask`・`bin/gunicorn`などの1行目（シバン）が`#!/app/.venv/bin/python`
    - `bin/python`が`/usr/local/bin/python3`へのシンボリックリンク（2段目にも、同じ場所に同じ版のPythonが要る）

```text
$ head -4 /app/.venv/bin/gunicorn
#!/app/.venv/bin/python
# -*- coding: utf-8 -*-
import sys
from gunicorn.app.wsgiapp import run
```

45. `migrations/`（9.23kB）・`entrypoint.sh`（210B）・`mkdir`と`chown`（中身のないフォルダだけなので0B）のレイヤーが続く。
46. 残りの`ENV`・`USER`・`EXPOSE`・`ENTRYPOINT`・`CMD`は、イメージの設定（`docker image inspect`の`Config`）に書かれるだけで、レイヤーは作らない。

`docker history fl-demonstro-web`（新しいものが上）：

```text
SIZE    CREATED BY
0B      CMD ["gunicorn" "--bind" ...]
0B      ENTRYPOINT ["entrypoint.sh"]
0B      EXPOSE 8000/tcp
0B      USER app
0B      ENV PATH=/app/.venv/bin:... APP_ENV=...
0B      RUN mkdir -p /app/instance && chown ...
210B    COPY docker/entrypoint.sh ...
9.23kB  COPY migrations ./migrations
52MB    COPY /app/.venv /app/.venv
0B      WORKDIR /app
8.85kB  RUN groupadd ... && useradd ...
0B      CMD ["python3"]
36B     RUN ... ln -svT ...
39.9MB  RUN ... （Pythonのビルドとインストール）
3.81MB  RUN ... apt-get install ca-certificates ...
78.9MB  # debian.sh --arch 'amd64' out/ 'trixie' ...
```

（`CMD ["python3"]`から下が`python:3.15-slim`。元のイメージの`ENV`の行は省いている）

47. レイヤーは10枚（元のイメージの4枚と、2段目の6枚）で、全体は約175MB。\
    アプリのために足した分は、ほぼ`.venv`の52MBだけ。
48. 出来上がるイメージに入らないもの：uvの実行ファイル、`pyproject.toml`・`uv.lock`・`README.md`・`src/`、uvのキャッシュ。\
    1段目のレイヤーは、ビルドキャッシュとして手元に残り、次のビルドで使われる（消すときは`docker builder prune`）。
49. イメージの設定：

```json
{
  "User": "app",
  "ExposedPorts": {"8000/tcp": {}},
  "Env": [
    "PATH=/app/.venv/bin:/usr/local/bin:...",
    "LANG=C.UTF-8",
    "PYTHON_VERSION=3.15.2",
    "PYTHON_SHA256=8b5536d2...",
    "PYTHONDONTWRITEBYTECODE=1",
    "PYTHONUNBUFFERED=1",
    "FLASK_APP=fl_demonstro",
    "APP_ENV=production",
    "INSTANCE_PATH=/app/instance"
  ],
  "Entrypoint": ["entrypoint.sh"],
  "Cmd": ["gunicorn", "--bind", "0.0.0.0:8000", "..."],
  "WorkingDir": "/app"
}
```

（ラベルは省略）

50. `LANG`・`PYTHON_VERSION`・`PYTHON_SHA256`は、元のイメージから引き継いだもの。
51. `PATH`には、`$PATH`をビルドのときに置き換えた後の文字列が保存される。\
    元のイメージの`PATH`に`/usr/local/bin`が2回入っているので、それもそのまま引き継いでいる（害はない）。

## 9. イメージとして書き出す

```text
#25 exporting to image
#25 exporting layers done
#25 writing image sha256:1a2bde453ed7... done
#25 naming to docker.io/library/fl-demonstro-web done
#26 resolving provenance for metadata file
 Image fl-demonstro-web Built
```

（キャッシュが全部効いたビルドのログ）

52. `exporting layers`：レイヤーを、Dockerのイメージの置き場所（ストレージドライバーはoverlay2）に書き出す。\
    キャッシュが効いたレイヤーは、すでにあるので書き出さない。
53. `writing image`：イメージの設定とレイヤーの一覧から、イメージのIDを計算して書く。
54. `naming to`：`fl-demonstro-web:latest`の名前を付ける。\
    前にこの名前だったイメージは、IDが変わったときだけ名前が外れ、`<none>`（dangling）として残る（消すときは`docker image prune`）。
55. `resolving provenance for metadata file`：ビルドの記録（provenance）を、bakeがComposeに返す結果のファイル用にまとめる。
56. Composeが`Image fl-demonstro-web Built`と出し、C（ネットワークとボリューム。`docs/6C.md`）に進む。
