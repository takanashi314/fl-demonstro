# docker compose up --buildの流れH：最初のリクエスト（6H）

`docs/06.md`のH（92〜97）を詳しくしたもの。

コードブロックの1行目に、抜き出したファイルと行番号を書いている。

ライブラリのコードは`.venv/lib/python3.15/site-packages/`からの相対パスで書く。

コードやログは、iPhoneの縦画面で読めるよう、改行やインデントを変えたり、一部を省いたりしている。

出力は、2026-11-27に手元で実行して取ったもの。ログの時刻はUTC（日本時間の9時間前）。

## 全体像

```text
curl（WSL）・ブラウザ
 → WSLの127.0.0.1:8000（docker-proxy）
 → webコンテナの172.18.0.3:8000
 → gunicornのワーカー（どちらか1つ）
 → Flask：セッションを開く → before_request
   → ビュー → after_request → セッションを保存
 → （必要なときだけ）Redisの172.18.0.2:6379
```

起動の後、WSLのcurlで次の4つを順に送り、その間Redisで`MONITOR`（届いたコマンドをすべて表示する）を動かしておいた。

| 順 | リクエスト | Redisに届いたコマンド |
| --- | --- | --- |
| 1 | `GET /`（Cookieなし） | なし |
| 2 | `GET /accounts/login`（Cookieなし） | `CLIENT SETINFO`×2・`SET` |
| 3 | `GET /`（2のCookieあり） | `CLIENT SETINFO`×2・`GET`・`SET` |
| 4 | `GET /nope` | なし |

1つ目のリクエストでは、Redisに一度もつながない。\
初めてつなぐのは、セッションに何かを書いたとき（表の2）か、Cookieのセッションを読むとき（表の3）。

## 1. WSLからコンテナまで

1. curlは、WSLの127.0.0.1:8000につなぐ。\
   ここで待っているのはdocker-proxy（`docs/6D.md`の5章）。\
   Windowsのブラウザで開くときは、WSLの機能で、Windowsの`localhost:8000`への接続がWSLの中に転送される。
2. docker-proxyは接続を受け取ると、webコンテナの172.18.0.3:8000に新しい接続を作り、2つの接続の間でデータを中継する。
3. 新しい接続の送り元は、ブリッジのアドレスの172.18.0.1になる。\
   webの中の`/proc/net/tcp`を見ると、8000番への接続はすべて172.18.0.1からだった。

```text
local              remote             st
030012AC:1F40      010012AC:D90C      06
030012AC:1F40      010012AC:D918      06
```

（16進数で、`030012AC`は172.18.0.3、`010012AC`は172.18.0.1、`1F40`は8000、`06`はTIME_WAIT。curlの4回分の接続のうち2つを載せている）

4. そのため、アプリから見ると、すべての利用者が172.18.0.1から来たように見える。
   - アクセスログの最初の項目（7章）
   - `request.remote_addr`
   - 回数制限のキー（`get_remote_address`）：`LIMITS:LIMITER/172.18.0.1/accounts.login/5/1/minute`のように、すべての利用者が1つのキーで数えられる（`docs/6E.md`の31）。
5. `ports`が`127.0.0.1:8000`なので、つなげるのはこのマシンからだけで、手元で試す分には困らない。\
   インターネットに公開するときは、前にリバースプロキシを置き、`TRUSTED_PROXY_COUNT`で本当の送り元を読み取る（`docs/6A.md`の5章）。\
   docker-proxyは`X-Forwarded-For`を付けないので、このままでは読み取れない。

## 2. ワーカーが受け取る

6. 2つのワーカーは同じソケットで待っていて、先に`accept()`したほうが受け取る（`docs/6G.md`の35）。\
   どちらが受け取るかは決まっていない。今回は、表の2をPID 9が、表の3をPID 8が受け取った（6章）。
7. ワーカーは、リクエストの行とヘッダーを読み、WSGIの`environ`（リクエストの情報の辞書）を作る。\
   `REMOTE_ADDR`は172.18.0.1、`wsgi.url_scheme`は`http`、`SERVER_SOFTWARE`は`gunicorn/27.0.1`。

```python
# gunicorn/workers/sync.py:174-194
resp, environ = wsgi.create(req, client, addr,
                            listener.getsockname(),
                            self.cfg)
resp.force_close()
self.nr += 1
...
respiter = self.wsgi(environ, resp.start_response)
try:
    ...
        for item in respiter:
            resp.write(item)
    resp.close()
finally:
    request_time = datetime.now() - request_start
    self.log.access(resp, req, environ, request_time)
```

（コメントと一部の分岐は省略）

8. `resp.force_close()`：レスポンスに`Connection: close`を付け、1つの接続で1つのリクエストだけを処理する。\
   `sync`ワーカーは1度に1つの接続しか扱えないので、接続をつなぎっぱなしにする（keep-alive）と、その間ほかのリクエストを受けられなくなるため。\
   ブラウザは、リクエストのたびに新しい接続を作る（CSSとJavaScriptはCDNから読むので、このアプリに来るのはHTMLとフォームの送信だけ）。
9. `self.wsgi(environ, resp.start_response)`：Flaskのアプリを呼ぶ（3章）。
10. レスポンスを書き終えた後、`finally`でアクセスログを出す（7章）。その後、接続を閉じる。

## 3. 1つ目：GET /（Cookieなし）

### セッションを開く

```python
# flask/ctx.py:390-399
# Open the session at the moment that the request
# context is available. ...
if self._session is None:
    session_interface = self.app.session_interface
    self._session = session_interface.open_session(
        self.app, self.request
    )

    if self._session is None:
        self._session = session_interface.make_null_session(
            self.app
        )
```

（コメントの一部は省略）

11. Flaskは、リクエストコンテキストを作ると、URLを照合する前に、セッションを開く。\
    `session_interface`は、`create_app()`の`server_session.init_app()`が差し替えた、Flask-SessionのRedis用のもの（`docs/6A.md`の7章の26）。

```python
# flask_session/base.py:332-339
def open_session(self, app, request):
    sid = request.cookies.get(
        app.config["SESSION_COOKIE_NAME"]
    )

    if not sid:
        sid = self._generate_sid(self.sid_length)
        return self.session_class(
            sid=sid, permanent=self.permanent
        )
```

（型ヒントとコメントは省略）

12. Cookieの`session`がないので、新しいセッションIDを作り、空のセッションを返す。Redisには問い合わせない。\
    IDは`secrets.token_urlsafe(32)`（32バイトの乱数をURLで使える文字にしたもの。43文字）。
13. `permanent=True`（Flask-Sessionの既定）なので、セッションの中身は`{"_permanent": True}`から始まる。

### before_requestとビュー

14. URLの`/`が、`main.index`に当たる。
15. `before_request`を登録順に呼ぶ（`docs/6A.md`の7章の27）。
    - CSRF（Flask-WTF）：`GET`は確かめる対象（`WTF_CSRF_METHODS`の`POST`・`PUT`・`PATCH`・`DELETE`）ではないので、何もしない。
    - 回数制限（Flask-Limiter）：`index`には制限がなく、全体の既定の制限もないので、記録先（Redis）に触らない。
16. `index()`が`render_template("main/index.html")`を呼ぶ。\
    テンプレートは、site-packagesの`fl_demonstro/templates/`から読まれる（`docs/6A.md`の7章の10）。\
    Jinja2はコンパイルしたテンプレートをアプリの中に取っておくので、コンパイルはワーカーごとに最初の1回だけ。
17. テンプレートの`current_user.is_authenticated`で、Flask-Loginがセッションを読む。\
    セッションが空なので、セッションの保護（5章）は飛ばし、`_user_id`もなく、「ログインしたままにする」のCookieもないので、ログインしていない利用者になる。\
    `flash.html`の`get_flashed_messages()`も、セッションの`_flashes`を見る。\
    どちらも読むだけなので、セッションは「読まれた（accessed）」が「変わった（modified）」ではない。

### after_requestとセッションの保存

```python
# flask/app.py:1316-1322
for name in chain(request.blueprints, (None,)):
    if name in self.after_request_funcs:
        for func in reversed(
            self.after_request_funcs[name]
        ):
            response = self.ensure_sync(func)(response)

if not self.session_interface.is_null_session(
    ctx._session
):
    self.session_interface.save_session(
        self, ctx._session, response
    )
```

18. `after_request`を、登録の逆順に呼ぶ。
    - セキュリティ用ヘッダー（`security.py`）：CSPなど4つを付ける。ログインしていないので`Cache-Control: no-store`は付けず、`SESSION_COOKIE_SECURE`が`False`なのでHSTSも付けない。
    - Flask-Login：セッションに`_remember`がないので、Cookieに触らない。
    - Flask-Limiter：ヘッダーを付ける設定（`RATELIMIT_HEADERS_ENABLED`）が既定で無効なので、何もしない。
19. 最後にセッションを保存する。

```python
# flask_session/base.py:289-305
if session.accessed:
    response.vary.add("Cookie")

if not session:
    if session.modified:
        self._delete_session(store_id)
        response.delete_cookie(key=name, domain=domain,
                               path=path)
        response.vary.add("Cookie")
    return

if not self.should_set_storage(app, session):
    return

self._upsert_session(app.permanent_session_lifetime,
                     session, store_id)
```

（コメントは省略）

20. セッションが読まれたので、`Vary: Cookie`を付ける（Cookieによって中身が変わるページだと、キャッシュするサーバーに伝える）。
21. `if not session`：Flask-Sessionのセッションは、中身が`_permanent`だけなら空として扱う（`flask_session/base.py:58-59`の`__bool__`）。\
    空で、変わってもいないので、Redisに書かず、`Set-Cookie`も付けずに終わる。
22. レスポンスのヘッダー：

```text

Server: gunicorn
Date: Thu, 26 Nov 2026 21:31:51 GMT
Connection: close
Content-Type: text/html; charset=utf-8
Content-Length: 2696
```

（`curl -D -`の出力。`Server`・`Date`・`Connection`はgunicorn、それ以外はFlaskが付けた）

23. リクエストコンテキストとアプリコンテキストを閉じる。\

## 4. 2つ目：GET /accounts/login（Redisに初めてつなぐ）

24. `login()`が`LoginForm()`を作り、テンプレートの`form.hidden_tag()`がCSRFトークンの隠しフィールドを出す。

```python
# flask_wtf/csrf.py:54-58
if field_name not in session:
    session[field_name] = hashlib.sha1(
        os.urandom(64)
    ).hexdigest()

try:
    token = s.dumps(session[field_name])
```

25. セッションに`csrf_token`がないので、乱数から40文字の16進数を作ってセッションに入れる（セッションが「変わった」になる）。\
    フォームに入るのは、それに`SECRET_KEY`で署名したもの（`s`は`URLSafeTimedSerializer`）。
26. 回数制限は`methods=["POST"]`なので、`GET`では記録先に触らない。
27. 保存のとき、セッションは空ではなく、変わってもいるので、`_upsert_session()`に進む。

```python
# flask_session/redis/redis.py:72-85
def _upsert_session(self, session_lifetime, session,
                    store_id):
    storage_time_to_live = total_seconds(session_lifetime)

    serialized_session_data = self.serializer.encode(
        session
    )

    self.client.set(
        name=store_id,
        value=serialized_session_data,
        ex=storage_time_to_live,
    )
```

（型ヒントとコメントは省略）

28. `self.client`は、`create_app()`の`Redis.from_url()`で作ったクライアント（`docs/6A.md`の7章の29）。\
    作ったときには接続プールを用意しただけなので、ここで初めて接続を作る。
    - `redis`という名前を、DockerのDNS（127.0.0.11）で172.18.0.2に変換する（`docs/6D.md`の28）。
    - 172.18.0.2:6379にTCPでつなぐ。送り元は172.18.0.3の空いているポート（今回は48618）。
    - redis-pyが、つないだ直後に、自分の名前と版を`CLIENT SETINFO`で知らせる。
29. その後、`SET`を送る。

```text
[0 172.18.0.3:48618] "CLIENT" "SETINFO" "LIB-NAME"
  "redis-py"
[0 172.18.0.3:48618] "CLIENT" "SETINFO" "LIB-VER"
  "7.4.1"
[0 172.18.0.3:48618] "SET"
  "session:neWx2IlrCAYW...LSRPKE"
  "\x82\xaa_permanent\xc3\xaacsrf_token\xd9(0d16...cc"
  "EX" "43200"
```

（`MONITOR`の出力。行頭の時刻を省き、長い値は`...`で縮めている。`[0 ...]`はDBの番号と送り元）

30. キーは`SESSION_KEY_PREFIX`の`session:`とセッションIDをつなげたもの。
31. 値は、セッションの辞書をmsgpack（Flask-Sessionの既定の形式）にしたもの。
    - `\x82`：要素が2つの辞書
    - `\xaa_permanent`：10バイトの文字列`_permanent`。続く`\xc3`は`True`
    - `\xaacsrf_token`：10バイトの文字列`csrf_token`。続く`\xd9(`は「長さ0x28（40）バイトの文字列」で、その後に25の40文字
32. `EX 43200`：`PERMANENT_SESSION_LIFETIME`（12時間）を秒にしたもの。Redisがこの時間で自動で消す。
33. レスポンスに`Set-Cookie`が付く。

```text
Set-Cookie: session=neWx2IlrCAYW...LSRPKE;
  Expires=Fri, 27 Nov 2026 09:31:52 GMT; HttpOnly;
  Path=/; SameSite=Lax
```

- `Expires`は12時間後。`permanent`なセッションなので、ブラウザを閉じても残る。
- `HttpOnly`・`SameSite=Lax`は`config.py`の設定。`SESSION_COOKIE_SECURE`が`false`なので、`Secure`は付かない。
- 値はセッションIDそのもの（`SESSION_USE_SIGNER`は既定で`False`）。32バイトの乱数なので、推測はできない。中身はRedisにあり、Cookieには入らない。

## 5. 3つ目：Cookieを付けてGET /

34. 今回は、表の2を受け取ったのとは別のワーカー（PID 8）が受け取った。\
    このワーカーのクライアントはまだ接続を持っていないので、新しい接続（送り元のポート48622）を作り、`CLIENT SETINFO`から始める。
35. セッションを開くとき、Cookieのセッションで`GET`する。

```python
# flask_session/base.py:348-354
store_id = self._get_store_id(sid)
saved_session_data = self._retrieve_session_data(
    store_id
)

if saved_session_data is not None:
    return self.session_class(saved_session_data, sid=sid)
```

（Redisに見つからないときは、2章と同じく新しいIDで空のセッションを作る）

36. テンプレートの`current_user`で、Flask-Loginがセッションの保護を確かめる。

```python
# flask_login/login_manager.py:395-402
# if the sess is empty, it's an anonymous user or just
# logged out so we can skip this
if sess and ident != sess.get("_id", None):
    if mode == "basic" or sess.permanent:
        if sess.get("_fresh") is not False:
            sess["_fresh"] = False
        session_protected.send(app)
        return False
```

37. `ident`は、送り元のアドレスとUser-Agentから作った値で、ログインしたときにセッションの`_id`に入る。\
    今のセッションは空ではない（`csrf_token`がある）のに`_id`がないので、条件に当たり、`_fresh`を`False`にする（保護の既定は`basic`）。\
    ログインしていなければ`_fresh`は使われないが、セッションは「変わった」になる。
38. 保存のときに、もう一度`SET`する。

```text
[0 172.18.0.3:48622] "CLIENT" "SETINFO" ...
[0 172.18.0.3:48622] "GET"
  "session:neWx2IlrCAYW...LSRPKE"
[0 172.18.0.3:48622] "SET"
  "session:neWx2IlrCAYW...LSRPKE"
  "\x83\xaa_permanent\xc3\xaacsrf_token\xd9(0d16...cc
   \xa6_fresh\xc2" "EX" "43200"
```

（`\x83`は要素が3つ、`\xa6_fresh`は6バイトの文字列、`\xc2`は`False`）

39. 中身が変わっていなくても、Flask-Sessionは`SESSION_REFRESH_EACH_REQUEST`（Flaskの既定で`True`）なので、毎回`SET`して期限を12時間に戻す（`should_set_storage()`）。\
    `Set-Cookie`も毎回付け直す（`permanent`で`SESSION_REFRESH_EACH_REQUEST`のとき。Flaskの`should_set_cookie()`）。\
    セッションが「最後の操作から12時間」で切れるのは、この2つのため。\
    25秒後に`TTL`を見ると、43175秒だった。
40. つまり、セッションのあるページを1回開くたびに、Redisに`GET`と`SET`の2回の往復が起きる。

## 6. 接続はつながったまま

41. Redisの`CLIENT LIST`では、webからの接続が2つ、使われずに残っていた（`MONITOR`自身の接続は省いている）。

```text
addr=172.18.0.3:48618 ... idle=27 ... cmd=set
  lib-name=redis-py lib-ver=7.4.1
addr=172.18.0.3:48622 ... idle=26 ... cmd=set
  lib-name=redis-py lib-ver=7.4.1
```

42. どちらのワーカーの接続かは、webの中の`/proc/<PID>/fd`と`/proc/net/tcp`のソケットの番号を突き合わせて確かめた。\
    PID 9が48618、PID 8が48622だった（`docs/6G.md`の6章の表）。
43. 接続プールは、使い終わった接続を閉じずに取っておき、次のコマンドで使い回す。\
    ワーカーはプロセスが別なので、接続も別々に持つ。
44. 回数制限のライブラリ（limits）は、セッションとは別のクライアントと接続プールを持つ（`RATELIMIT_STORAGE_URI`から自分で作る）。\
    回数制限が働くリクエスト（ログインのPOSTなど）を受けると、ワーカーごとにもう1つ接続が増える。

## 7. アクセスログ

45. 形式は、gunicornの既定の`%(h)s %(l)s %(u)s %(t)s "%(r)s" %(s)s %(b)s "%(f)s" "%(a)s"`（`gunicorn/config.py:1521`）。

```text
172.18.0.1 - - [26/Nov/2026:21:31:51 +0000]
  "GET / HTTP/1.1" 200 2696 "-" "curl/8.5.0"
172.18.0.1 - - [26/Nov/2026:21:31:52 +0000]
  "GET /accounts/login HTTP/1.1" 200 4002 "-"
  "curl/8.5.0"
172.18.0.1 - - [26/Nov/2026:21:31:53 +0000]
  "GET / HTTP/1.1" 200 2696 "-" "curl/8.5.0"
172.18.0.1 - - [26/Nov/2026:21:31:54 +0000]
  "GET /nope HTTP/1.1" 404 2649 "-" "curl/8.5.0"
```

- `h`：送り元のアドレス（`REMOTE_ADDR`）。`X-Forwarded-For`などのヘッダーでは書き換わらない。
- `l`：常に`-`（昔のログの形式に合わせるための欄）。
- `u`：Basic認証のユーザー名。使っていないので`-`。
- `t`：時刻。
- `r`：リクエストの行。
- `s`：ステータスコード。
- `b`：レスポンスの本文のバイト数。
- `f`：Referer。curlは送らないので`-`。
- `a`：User-Agent。

46. アクセスログは、レスポンスを書き終えた後に出る（2章の10）。\
    404のようなエラーでも出て、`errors.py`のエラー画面（2649バイト）を返したことが分かる。
47. ブラウザで開くと、ページのほかに`/favicon.ico`も自動で取りにくる。\
    このアプリには`static/`もfaviconのルートもないので、その行は404になる。
48. アクセスログは標準出力、gunicornのほかのログは標準エラーに出る。どちらも`docker compose logs`で見られる（`docs/6I.md`の1章）。
