# docker compose up --buildの流れG：gunicornが起動する（6G）

`docs/06.md`のG（83〜91）を詳しくしたもの。

コードブロックの1行目に、抜き出したファイルと行番号を書いている。

ライブラリのコードは`.venv/lib/python3.15/site-packages/`からの相対パスで書く（gunicorn 27.0.1）。

コードやログは、iPhoneの縦画面で読めるよう、改行やインデントを変えたり、一部を省いたりしている。

出力は、2026-11-27に手元で実行して取ったもの。ログの時刻はUTC（日本時間の9時間前）。

## 全体像

gunicornは、1つのmaster（arbiter）と、masterがforkした2つのワーカーで動く。

```text
PID 1: gunicorn master
 ├ 設定を読む（1章）
 ├ 0.0.0.0:8000で待ち受けるソケットを作る（2章）
 ├ fork → PID 8: ワーカー → create_app() → 接続を待つ
 ├ fork → PID 9: ワーカー → create_app() → 接続を待つ
 ├ 管理用のソケットを開く（4章）
 └ ワーカーを見張るループ（6章）
```

- masterは、アプリを読み込まず、リクエストも処理しない。ソケットを持ち、ワーカーを作って見張るだけ。
- ワーカーは、それぞれが`fl_demonstro`をimportして`create_app()`を呼び、同じソケットから接続を受け取る（5章）。


   - 設定ファイル：`-c`がなければ、作業フォルダの`gunicorn.conf.py`（`gunicorn/config.py:655-660`）。`/app`にはないので読まない。

3. 書いていない設定は既定値になる。このアプリの動きに関係するもの：
   - `--worker-class`：`sync`
   - `--timeout`：30秒（6章）
   - `--graceful-timeout`：30秒（`docs/6I.md`の2章）
   - `--backlog`：2048（2章）
   - `--preload`：なし（11）

   もし`/app/fl_demonstro/`があれば、site-packagesより先に見つかってしまう。2段目に`src/`を持っていかないのは、この点でも安全。

## 2. masterが起動する

5. `Arbiter`が作られ、環境変数`SERVER_SOFTWARE`に`gunicorn/27.0.1`を入れる（`gunicorn/arbiter.py:54`）。
6. `start()`が`Starting gunicorn 27.0.1`を出し、シグナルのハンドラーを登録する。

7. 対象は`HUP QUIT INT TERM TTIN TTOU USR1 USR2 WINCH`と`CHLD`。\
   ハンドラーはシグナルをキューに入れるだけで、処理はメインのループ（6章）で行う。\
   PID 1でも、ハンドラーを登録したシグナルは届く（`docs/6F.md`の46）。

### 待ち受けるソケットを作る

```python
# gunicorn/sock.py:42-61
def set_options(self, sock, bound=False):
    sock.setsockopt(socket.SOL_SOCKET,
                    socket.SO_REUSEADDR, 1)
    ...
    if not bound:
        self.bind(sock)
    sock.setblocking(0)

    if hasattr(sock, "set_inheritable"):
        sock.set_inheritable(True)

    if not self._is_listening(sock):
        sock.listen(self.conf.backlog)
    return sock
```

（`SO_REUSEPORT`の部分とコメントは省略）

8. `--bind 0.0.0.0:8000`から、TCPのソケットを1つ作る。
   - `SO_REUSEADDR`：前のプロセスの接続が`TIME_WAIT`で残っていても、同じポートでbindできるようにする。
   - `setblocking(0)`：ノンブロッキングにする。ワーカーは、接続が来ていなければ待たずに戻ってくる`accept()`を使う（5章）。
   - `set_inheritable(True)`：forkした子（ワーカー）に引き継げるようにする。
   - `listen(2048)`：まだ`accept()`されていない接続を、2048個まで待たせておける。
9. `Listening at: http://0.0.0.0:8000 (1)`を出す。`(1)`はmasterのPID。
10. `Using worker: sync`を出す。
11. `--preload`がないので、masterはアプリを読み込まない（`fl_demonstro`をimportしない）。\
    `--preload`を付けると、masterで1回だけ`create_app()`を呼び、forkでワーカーに引き継ぐ。\
    起動は速くなるが、forkの前に作ったDBやRedisの接続をワーカー同士で共有してしまう危険があり、コードを変えたときのreload（HUP）でもアプリが読み直されない。

## 3. ワーカーをforkする

```python
# gunicorn/arbiter.py:726-753
def spawn_worker(self):
    self.worker_age += 1
    worker = self.worker_class(
        self.worker_age, self.pid, self.LISTENERS,
        self.app, self.timeout / 2.0, self.cfg, self.log
    )
    self.cfg.pre_fork(self, worker)

    pid = os.fork()
    if pid != 0:
        worker.pid = pid
        self.WORKERS[pid] = worker
        self._stats['workers_spawned'] += 1
        return pid

    for sibling in self.WORKERS.values():
        sibling.tmp.close()

    worker.pid = os.getpid()
    try:
        util._setproctitle("worker [%s]" % self.proc_name)
        self.log.info("Booting worker with pid: %s",
                      worker.pid)
        ...
        worker.init_process()
        sys.exit(0)
```

（コメントと例外の処理は省略）

12. `manage_workers()`が、`--workers 2`に足りない分だけ`spawn_worker()`を呼ぶ。\
    1つforkするごとに、0〜0.1秒の乱数の時間だけ待つ（`gunicorn/arbiter.py:786-788`）。
13. forkの前に、masterの中でワーカーのオブジェクトを作る。\
    このとき、ワーカーの生存確認に使う一時ファイル（`WorkerTmp`）を作る（6章）。
14. `os.fork()`は、masterのプロセスを丸ごと複製する。\
    親（master）には子のPIDが返り、`WORKERS`に登録して戻る。\
    子（ワーカー）には0が返り、以下に進む。待ち受けのソケットも、forkでそのまま子に引き継がれる。
15. 子は、先に作られたほかのワーカーの一時ファイルを閉じてから、`Booting worker with pid: 8`を出す。\
    このログはアプリを読み込む前に出るので、「起動が終わった」印にはならない（7章）。
16. `_setproctitle()`は、`setproctitle`パッケージが入っていなければ何もしない（`gunicorn/util.py:69-71`）。\
    入れていないので、`ps`でもmasterとワーカーは同じコマンドラインに見え、PPIDでしか区別できない（`docs/6F.md`の最後の表）。

## 4. 管理用のソケット

17. 2つのワーカーをforkし終えてから、masterが管理用のソケットを開く（`gunicorn/arbiter.py:247-251`）。\
    サーバーはasyncioで書かれていて、masterの中の別スレッドで動く。forkの前にスレッドを動かすと、forkした子でロックが壊れることがあるので、forkの後に始める。
18. 場所は、`XDG_RUNTIME_DIR`があればその中、なければ`$HOME/.gunicorn/gunicorn.ctl`。

```python

    if xdg_runtime and os.path.isdir(xdg_runtime):
        return os.path.join(xdg_runtime, 'gunicorn.ctl')

    home = os.path.expanduser('~')
    gunicorn_dir = os.path.join(home, '.gunicorn')
    return os.path.join(gunicorn_dir, 'gunicorn.ctl')
```

（docstringとコメントは省略）

19. コンテナには`XDG_RUNTIME_DIR`がなく、`HOME`はDockerが入れた`/home/app`なので、`/home/app/.gunicorn/gunicorn.ctl`になる。\
    `useradd --create-home`で`/home/app`を作っていなければ、`Failed to start control socket`の警告が出る（gunicornは動き続ける）。
20. ソケットの権限は既定で`0600`（`--control-socket-mode`）、フォルダは`0700`。\
    同じ`app`ユーザーで`gunicornc`（`/app/.venv/bin/gunicornc`）を動かすと、ワーカーの状態を見たり、数を変えたりできる。

```text

drwx------ 2 app app 4096 Nov 26 21:31 .
srw------- 1 app app    0 Nov 26 21:31 gunicorn.ctl
```

21. このソケットはコンテナの中の書き込み可能なレイヤーにあるので、コンテナを作り直すと消える（起動のたびに作り直されるので困らない）。

## 5. ワーカーがアプリを読み込む

```python
# gunicorn/workers/base.py:88-146

    if self.cfg.env:
        for k, v in self.cfg.env.items():
            os.environ[k] = v

    util.set_owner_process(self.cfg.uid, self.cfg.gid,
                           initgroups=self.cfg.initgroups)
    util.seed()

    self.PIPE = os.pipe()
    ...
    self.init_signals()
    ...
    self.load_wsgi()
    ...
    self.booted = True
    self.run()
```

（`close_on_exec`の設定、reloaderの部分、コメントは省略）

22. `set_owner_process()`：`--user`・`--group`を指定していないので、uidとgidは変わらない（`USER app`のまま）。
23. `util.seed()`：乱数の種を作り直す。forkした子は親と同じ乱数の状態を持つので、そのままだと2つのワーカーが同じ乱数を出してしまう。
24. `os.pipe()`：自分を起こすためのパイプ。シグナルを受けたときに、待っている`select()`から抜けるのに使う（`set_wakeup_fd`）。
25. `init_signals()`：ワーカーのシグナルのハンドラーを登録する。

```python
# gunicorn/workers/base.py:169-179
signal.signal(signal.SIGQUIT, self.handle_quit)
signal.signal(signal.SIGTERM, self.handle_exit)
signal.signal(signal.SIGINT, self.handle_quit)
signal.signal(signal.SIGWINCH, self.handle_winch)
signal.signal(signal.SIGUSR1, self.handle_usr1)
signal.signal(signal.SIGABRT, self.handle_abort)

signal.siginterrupt(signal.SIGTERM, False)
signal.siginterrupt(signal.SIGUSR1, False)
```

（コメントは省略）

26. SIGTERMは`self.alive = False`にするだけ（今のリクエストを終えてから止まる）。SIGQUIT・SIGINTはすぐに終わる。SIGABRTは終了ステータス1で終わる（6章のタイムアウト）。\
    `siginterrupt(SIGTERM, False)`で、SIGTERMを受けても、リクエストの処理中のシステムコール（ソケットの読み書きなど）を中断させない。
27. `load_wsgi()`：`self.app.wsgi()`から`util.import_app("fl_demonstro:create_app()")`を呼ぶ（`docs/6A.md`の7章の8）。
    - `fl_demonstro`をimportする。ワーカーごとに別のプロセスなので、`config.py`の評価もワーカーごとに起きる。
    - `create_app()`を呼ぶ。エンジンやRedisのクライアントも、ワーカーごとに別々に作られる。
    - `SECRET_KEY`は環境変数から来るので、2つのワーカーで同じ値になり、どちらのワーカーが作ったCSRFトークンも、もう一方で確かめられる。
28. 読み込めたら`self.booted = True`にして、`run()`（接続を待つループ）に入る。ここがそのワーカーの起動の終わり。

### 読み込みに失敗したとき

```python
# gunicorn/arbiter.py:681-686

    reason = "Worker failed to boot."
    raise HaltServer(reason, self.WORKER_BOOT_ERROR)
if exitcode == self.APP_LOAD_ERROR:
```

29. `create_app()`などで例外が出ると、ワーカーは終了ステータス3（`WORKER_BOOT_ERROR`）で終わる。\
    `fl_demonstro:create_app()`の形が正しくない・見つからない（`AppImportError`）ときは4（`APP_LOAD_ERROR`）。
30. masterは、ワーカーが3か4で終わると、作り直さずにgunicorn全体を止める（同じ失敗を繰り返さないため）。\
    PID 1が終わるのでコンテナが止まり、`restart: unless-stopped`でDockerが起動し直す（`docs/6F.md`の9〜11）。
31. ただし、`create_app()`の失敗のほとんどは、先に`flask db upgrade`（`docs/6F.md`の19）で起きるので、ふつうはワーカーまで来ない。

## 6. 接続を待つループと、masterの見張り

### ワーカーのループ

```python
# gunicorn/workers/sync.py:58-80
def run_for_one(self, timeout):
    listener = self.sockets[0]
    while self.alive:
        self.notify()

        try:
            self.accept(listener)
            continue

        except OSError as e:
            if e.errno not in (errno.EAGAIN,
                               errno.ECONNABORTED,
                               errno.EWOULDBLOCK):
                raise

        if not self.is_parent_alive():
            return

        try:
            self.wait(timeout)
        except StopWaiting:
            return
```

（コメントは省略）

32. 待ち受けのソケットが1つなので、`run_for_one()`を使う。
33. まず`accept()`を試す。ソケットはノンブロッキングなので、接続が来ていなければ`EAGAIN`ですぐ戻る。\
    接続を受け取ったら、そのリクエストを処理してから（`docs/6H.md`の2章）、すぐ次の`accept()`を試す。
34. 来ていなければ、`wait()`の`select()`で、ソケットか自分を起こすパイプ（24）に何か来るまで待つ。\
    待つ時間の上限は、`--timeout`の半分の15秒（`spawn_worker()`の`self.timeout / 2.0`）。
35. 2つのワーカーは、同じソケットで`select()`している。\
    接続が来ると両方が起きることがあり、先に`accept()`したほうが受け取る。もう一方は`EAGAIN`になって、また待つ。
36. `is_parent_alive()`：親のPIDが変わっていたら（masterが死んでいたら）、ループを抜けて終わる。

### 生存確認の一時ファイル

```python
# gunicorn/workers/workertmp.py:42-47
def notify(self):
    new_time = time.monotonic()
    os.utime(self._tmp.fileno(), (new_time, new_time))

def last_update(self):
    return os.fstat(self._tmp.fileno()).st_mtime
```

37. ワーカーは、ループを回るたびに`notify()`で、一時ファイルの更新日時を「今の時刻（`time.monotonic()`）」に書き換える。\
    待っている間も、15秒ごとに`select()`から戻ってくるので、書き換えは続く。
38. 一時ファイルは`/tmp`に`wgunicorn-`で始まる名前で作られ、すぐに消される（`gunicorn/workers/workertmp.py:23・34`）。\
    消してもファイルディスクリプタは開いたままなので、masterとワーカーの間でだけ使える。

```text
$ ls -l /proc/1/fd    （master）
3 -> socket:[5486854]       待ち受けのソケット
4 -> /tmp/wgunicorn-epl8q_h8 (deleted)
5 -> /tmp/wgunicorn-lvqnmpaq (deleted)
6 -> anon_inode:[eventpoll] 管理用ソケットのasyncio
...
$ ls -l /proc/8/fd    （ワーカー）
```

### masterのループ

```python
# gunicorn/arbiter.py:603-622
def murder_workers(self):
    if not self.timeout:
        return
    workers = list(self.WORKERS.items())
    for (pid, worker) in workers:
        try:
            if (time.monotonic()
                    - worker.tmp.last_update()
                    <= self.timeout):
                continue
        except (OSError, ValueError):
            continue

        if not worker.aborted:
            self.log.critical("WORKER TIMEOUT (pid:%s)",
                              pid)
            worker.aborted = True
            self.kill_worker(pid, signal.SIGABRT)
        else:
            self.kill_worker(pid, signal.SIGKILL)
```

（docstringは省略）

39. masterのループ（`gunicorn/arbiter.py:253-274`）は、シグナルを最大1秒待ち、来たシグナルを処理してから、`murder_workers()`と`manage_workers()`を呼ぶ。これを繰り返す。
40. `murder_workers()`：一時ファイルの更新日時が30秒（`--timeout`）より古いワーカーに、`WORKER TIMEOUT`を出してSIGABRTを送る。次の回でもまだいれば、SIGKILL。
41. `sync`ワーカーは、リクエストを処理している間はループを回らないので、`notify()`もしない。\
    1つのリクエストに30秒以上かかると、処理の途中でワーカーが止められ、接続は切れる。
42. `manage_workers()`：ワーカーが2つより少なければ（止められた・落ちたなど）、forkして足す。
43. ワーカーが終わるとSIGCHLDが届き、`reap_workers()`が`waitpid()`で回収して、`WORKERS`から外す（終了ステータスが3か4なら、5章の30）。

## 7. 起動の終わり

44. 2つのワーカーが`run()`に入れば、起動は終わり。\
    ただし、gunicornはそのときにログを出さない（`Booting worker`は読み込みの前。15）。
45. `Control socket listening at`も、forkの直後にmasterが出すので、ワーカーの読み込みが終わった印ではない。
46. 確かめるには、リクエストを送ってアクセスログが出るかを見る。\
    自動で確かめるなら、`compose.yaml`の`healthcheck:`で定期的にリクエストを送る方法がある（今は書いていない）。
47. この時点でも、Redisにはまだつないでいない（`docs/6F.md`の全体像）。最初のリクエストは`docs/6H.md`。
